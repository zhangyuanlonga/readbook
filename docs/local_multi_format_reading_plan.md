# 本地多格式阅读开发方案

更新时间：2026-04-16  
当前状态：阶段 D 执行中  
用途：为当前项目建立一套可持续演进的本地多格式阅读能力方案，覆盖 `txt`、`epub`、`md`、`html`、`pdf`、`mobi`、`azw`、`azw3` 的导入、解析、索引、存储和阅读链路。

## 0. 执行摘要

当前项目已经具备本地阅读基础能力，但本地正文链路仍存在设计债：

- `txt` 在索引阶段主要写入目录和偏移，阅读阶段再按 offset 回读正文
- `epub` 在索引阶段主要建立目录和 `sourceRef`，阅读阶段再按章节资源懒解析
- 本地阅读虽然与在线书源是两条独立链路，但本地侧仍保留了“进入章节时再补正文”的实现

这套做法在当前 `txt/epub` 范围内还能工作，但如果继续把 `md/html/pdf/mobi/azw/azw3` 接入同一模式，会带来三个问题：

- 新格式接入成本会越来越高
- `ready` 状态不再等于“可完整离线阅读”
- 阅读页会持续承担本该属于索引阶段的格式解析成本

本方案的核心结论是：

1. 本地图书应统一收口到“索引完成即完整可读”的主路径。
2. 本地阅读不应继续扩散正文懒解析模型。
3. 新格式接入必须先完成本地章节模型和索引语义收口，再做格式扩展。

## 1. 当前实现判断

### 1.1 本地与在线书源是两条链路

当前代码中：

- 本地阅读走 `LocalContentProvider`
- 在线书源走 `ChapterContentService`

两者不是同一套正文加载实现。

这意味着当前本地正文懒解析不是“在线书源逻辑误复用”，而是本地阅读自己的历史设计。

### 1.2 当前本地懒解析真实存在

当前本地阅读中：

- `txt` 索引后章节 `content` 可能为空，正文在阅读时按偏移回读
- `epub` 索引后章节 `content` 也可能为空，正文在阅读时再执行章节资源解析

这会导致：

- 目录建立完成不等于正文可读
- 阅读页承担文件读取和格式解析成本
- 某些问题只有真正点击章节时才暴露

### 1.3 当前已支持格式

当前对外稳定支持：

- `txt`
- `epub`

其中：

- `txt` 是纯文本链路
- `epub` 是当前唯一真正承载本地图文混排的主格式

## 2. 目标定义

本地多格式阅读的目标不是“让选择器多几个扩展名”，而是建立一套统一、可维护、可验证的本地阅读架构。

目标拆分如下：

### 2.1 产品目标

- 支持用户导入 `txt`、`epub`、`md`、`html`、`pdf`、`mobi`、`azw`、`azw3`
- 已索引完成的本地图书在断网下可完整阅读
- 图文顺序以结构化文档模型为准，而不是字符串兼容兜底
- 文件导入失败时给出明确错误边界，而不是笼统提示“打不开”

### 2.2 架构目标

- 本地阅读统一为“导入/重索引阶段解析，阅读阶段只读库”
- `LocalBookIndexStatus.ready` 语义收口为“目录和正文都已可读”
- 所有本地格式统一落到 `LocalParsedBook -> LocalChapter -> ReaderDocument`
- 阅读页不再调用格式 parser 执行正文主解析

### 2.3 演进目标

- 新格式接入时尽量复用现有章节模型和阅读 UI
- 减少按格式分叉的临时判断
- 为后续 OCR、批量转换、封面抽取、元数据增强预留位置

## 3. 总体原则

### 3.1 本地图书主路径

统一主路径应为：

1. 用户选择文件
2. 系统识别格式
3. 文件复制到托管目录
4. 执行格式解析或格式转换
5. 生成统一章节模型
6. 一次性写入书籍、章节、结构化文档、图片资源
7. 阅读时直接从数据库读取

### 3.2 本地阅读不再依赖正文懒解析

允许保留非常有限的“临时预览”能力，但它只能作为：

- 导入后索引尚未完成时的预览
- 极端异常情况下的诊断工具

不能再作为本地图书正式阅读主路径。

### 3.3 `ready` 状态必须收口

后续约束：

- `pending`：已导入，尚未索引
- `indexing`：正在解析
- `ready`：正文和目录都已可用
- `stale`：源文件变化，需要重建
- `failed`：解析失败或转换失败

`ready` 不允许再表示“目录可用但正文需要点击章节后再补全”。

## 4. 支持格式分组策略

建议不要把八种格式平铺处理，而应按内容形态分组。

### 4.1 纯文本类

- `txt`
- `md`

特点：

- 正文本质可归一到文本块和标题结构
- 图片支持弱于容器格式
- 最容易先落地

### 4.2 HTML 文档类

- `html`

特点：

- 自带 DOM 结构
- 天然适合转换为 `ReaderDocument`
- 资源路径处理比纯文本更复杂

### 4.3 电子书容器类

- `epub`
- `mobi`
- `azw`
- `azw3`

特点：

- 可能包含目录、元数据、封面、图片、脚注、样式资源
- 更适合先抽出标准内容结构，再统一进入章节模型

### 4.4 固定版式类

- `pdf`

特点：

- 章节结构不天然存在
- 文本抽取质量高度依赖文件类型
- 图片型 PDF 与文本型 PDF 需要区别处理

## 5. 统一模型设计

### 5.1 书籍格式枚举

需要扩展 `LocalBookFormat`：

- `txt`
- `md`
- `html`
- `epub`
- `mobi`
- `azw`
- `azw3`
- `pdf`

### 5.2 章节产物要求

所有格式在索引阶段都必须产出：

- `title`
- `content`
- `imageUrls`
- `document`
- 必要时的 `sourceRef`

其中约束如下：

- `content` 不能在 `ready` 章节里长期为空
- `document` 是图文主表达
- `imageUrls` 是兼容层和纯图片章节识别的辅助手段
- `sourceRef` 可以保留用于追踪来源，但不能作为阅读时再次解析正文的前提

### 5.3 图片资源管理

所有本地图片资源统一落到托管目录：

- EPUB/Kindle 容器内图片解包到资产目录
- HTML 相对路径图片复制到资产目录
- Markdown 相对路径图片复制到资产目录
- PDF 图片抽取结果按需落地到资产目录

目标是保证：

- 原始导入文件缺失后，托管副本仍可阅读
- 阅读页只消费稳定的本地资源 URL 或相对路径

### 5.4 书籍信息提取要求

本地多格式阅读不只要提章节，还要尽量在导入/索引阶段补齐简要书籍信息。

基础书籍信息字段建议统一为：

- `title`
- `author`
- `description`
- `coverPath`
- `language`

其中：

- `title` 是必填字段，提取失败时允许回退到文件名
- `author`、`description`、`language` 允许为空，但要保留后续补写能力
- `coverPath` 一旦提取成功，应统一落到托管目录，不依赖原始文件实时解析

对 EPUB 的要求更高：

- 索引阶段必须自动提取书名
- 索引阶段必须自动提取作者
- 索引阶段应尽量提取简介或摘要
- 索引阶段必须自动提取封面
- 当元数据缺失时，要有明确 fallback 规则，不能默默空白

## 6. 各格式落地策略

### 6.1 `txt`

目标：

- 保留当前自动切章和编码兼容能力
- 去掉“索引后只存 offset，阅读时再回读正文”的主路径

实施策略：

- 索引阶段直接写入完整章节正文
- offset 保留为可选调试字段，不再作为阅读时必需条件
- 大文件仍可流式切章，但切完后立即落完整正文

结果要求：

- `txt` 在 `ready` 后应完全脱离源文件按章节读取逻辑

### 6.2 `md`

目标：

- 支持 Markdown 书籍和笔记型文档阅读

实施策略：

- 使用 Markdown 解析能力转为 HTML 或中间 AST
- 将标题、段落、列表、引用、代码块、图片转换为 `ReaderDocument`
- 章节默认按一级或二级标题拆分
- 无有效标题时整本作为单章

结果要求：

- 支持基础图文混排
- 支持相对路径图片
- 支持本地文件图片复制

### 6.3 `html`

目标：

- 支持单文件 HTML 导入阅读

实施策略：

- 解析 DOM
- 删除 `script/style` 等非正文节点
- 提取标题、段落、列表、引用、图片、表格的降级表达
- 处理相对路径图片和本地资源复制
- 默认单文件一章，必要时支持按 `h1/h2` 拆章

结果要求：

- 单文件图文内容可稳定阅读
- 阅读页不再依赖文件系统实时解析 HTML

### 6.4 `epub`

目标：

- 保留当前 EPUB 兼容能力
- 消除阅读时 `parseChapter` 懒解析主路径
- 自动提取简要书籍信息和封面

实施策略：

- 索引阶段遍历 spine
- 每一章直接生成 `content`、`imageUrls`、`document`
- 索引阶段优先从 OPF/DC 元数据提取：
  - `title`
  - `author`
  - `description`
  - `language`
- 索引阶段自动解析封面：
  - 优先读取明确的 cover manifest/meta 声明
  - 其次回退到常见封面资源命名和首页大图规则
- 当书籍信息缺失时执行 fallback：
  - `title` 回退为文件名或首个有效章节标题
  - `author` 回退为空，不伪造
  - `description` 回退为空，不用正文前几段硬拼简介
- 封面、元数据、图片资源在索引阶段准备完成
- 阅读阶段只读数据库中的章节正文和结构化文档

结果要求：

- `epub` 从“建目录后按需解析正文”升级为“索引完成即完整可读”
- 详情页和书架在索引完成后可直接显示自动提取的书名、作者和封面

### 6.5 `pdf`

目标：

- 优先支持文本型 PDF 阅读

实施策略：

- V1 只支持可提取文本的 PDF
- 通过 PDF 文本抽取能力按页读取文本
- 再按标题、空白页、分页规则构建章节
- 扫描版或图片版 PDF 暂不纳入稳定支持承诺

结果要求：

- 文本型 PDF 可导入、可分章、可离线阅读
- 失败提示明确区分“加密 / 无文本层 / 抽取失败”

### 6.6 `mobi`、`azw`、`azw3`

目标：

- 在无 DRM 前提下提供 Kindle 容器书籍导入能力

实施策略：

- 不建议把这三种格式直接绑定到阅读层
- 应优先走“容器解析/转换 -> HTML/EPUB 风格中间结构 -> 统一章节模型”
- 统一封面、目录、图片资源和正文提取流程

结果要求：

- 仅承诺支持无 DRM 文件
- `azw` 兼容度允许低于 `mobi/azw3`
- 转换失败要有明确错误信息，不要伪装成“正文为空”

## 7. 依赖与合规策略

### 7.1 依赖引入原则

优先级如下：

1. 纯 Dart 或 Flutter 跨平台能力优先
2. 许可证清晰、分发风险低的依赖优先
3. 可接受“先做受限支持”，不接受模糊承诺“全格式稳定支持”

### 7.2 许可证边界

需要在立项时明确：

- `pdf` 的文本抽取库若采用商业许可依赖，需要单独确认
- `mobi/azw/azw3` 相关库若为 LGPL 或其他强约束许可证，需要先做合规评估
- 不应在未明确许可证影响前，直接把受限依赖接入正式发布链路

### 7.3 产品边界

对外口径建议：

- `txt`、`epub`、`md`、`html`：稳定支持
- `pdf`：支持文本型 PDF
- `mobi`、`azw`、`azw3`：支持无 DRM 文件，兼容性持续完善

### 7.4 当前 PDF 选型结论

当前项目在阶段 C 首版中采用：

- `pdf_text_extract`

当前结论：

- 许可证：MIT
- 平台：Android、iOS
- 当前实现范围：文本型 PDF 提取，不包含 OCR
- 当前实现策略：按页切章，若页首检测到明显章节标题则优先用章节标题

当前残余风险：

- 依赖发布者为 `pub.dev` 未认证发布者
- 当前不支持桌面端和 Web 的 PDF 文本抽取
- 扫描版、图片版、无文本层 PDF 仍按失败处理，不做伪兼容

### 7.5 当前 Kindle 容器选型结论

当前项目在阶段 D 首版中采用：

- `dart_mobi`

当前结论：

- 许可证：LGPL-3.0
- 当前实现范围：`mobi`、`azw`、`azw3`
- 当前实现前提：仅支持无 DRM 文件
- 当前实现策略：容器正文转 HTML，再复用现有本地 HTML/Markdown 解析层

当前残余风险：

- 依赖作者在 README 中明确声明“not thoroughly tested”
- 当前样本覆盖仍以回归样本和 fake extractor 为主
- 当前已覆盖 `mobi/azw3` 稳定回归样本，`azw` 已补基础正向样本，但仍不视为完全稳定
- `azw` 兼容度仍视为增强项，不宣称与 `mobi/azw3` 等同稳定

## 8. 推荐实施顺序

### 阶段 A：先收口本地正文主路径

目标：

- 让本地 `ready` 真正表示“可完整阅读”

任务：

- `txt` 改为索引阶段写入完整正文
- `epub` 改为索引阶段写入完整正文和结构化文档
- 精简 `LocalChapterContentService`
- 将正文懒解析退为兼容/临时预览逻辑

阶段完成标准：

- `txt/epub` 阅读阶段不再依赖文件级正文解析

### 阶段 B：低风险扩格式

目标：

- 快速验证新架构的可扩展性

任务：

- 新增 `md`
- 新增 `html`
- 补充本地图文顺序和相对资源测试

阶段完成标准：

- `md/html` 导入后可直接离线阅读

### 阶段 C：补 `pdf`

目标：

- 支持文本型 PDF

任务：

- 选型 PDF 文本抽取能力
- 定义章节切分策略
- 明确错误边界和 UI 提示

阶段完成标准：

- 文本型 PDF 可稳定导入和阅读

### 阶段 D：补 Kindle 容器格式

目标：

- 支持无 DRM 的 `mobi/azw/azw3`

任务：

- 评估依赖和许可证
- 建立容器转换层
- 与统一章节模型打通

阶段完成标准：

- 至少 `mobi/azw3` 样本可稳定导入
- `azw` 作为兼容增强项持续迭代

## 10. 代码改造清单

### 9.1 导入层

- 扩展文件选择器支持的扩展名
- 扩展 `LocalBookImportService._resolveFormat`
- 扩展导入失败提示和格式边界提示

### 9.2 存储层

- 扩展 `LocalBookStorageService._extensionForFormat`
- 为 HTML/Markdown/PDF/Kindle 容器资源建立托管策略
- 为多格式资产目录提供统一清理逻辑

### 9.3 索引层

- 扩展 `LocalBookIndexService` 的 parser 注册表
- 新增格式 parser 或 converter
- 收口 `ready` 状态语义

### 9.4 阅读层

- 精简 `LocalChapterContentService`
- 去掉本地章节正文主路径懒解析
- 保留结构化文档直出能力

### 9.5 测试层

- 为每种格式补导入测试
- 为每种格式补索引产物测试
- 为图文顺序和图片资源补回归测试
- 为失败场景补错误消息测试

## 11. 风险与对策

### 10.1 风险：格式支持看起来简单，实际结构差异大

对策：

- 先统一模型，再扩格式
- 先做低风险格式，再做复杂容器

### 10.2 风险：依赖许可证影响发布

对策：

- 在 `pdf` 和 Kindle 容器格式落地前先完成依赖合规评估
- 不能在未确认前把受限库直接纳入正式方案承诺

### 10.3 风险：大文件索引耗时上升

对策：

- 保留流式处理
- 允许分阶段入库
- 但最终仍要求 `ready` 前完整正文已写入数据库

### 10.4 风险：PDF 和 Kindle 格式样本差异太大

对策：

- 明确第一阶段仅承诺受限支持
- 建立样本集，不用模糊口径掩盖兼容边界

## 12. 验收标准

方案落地后，至少应满足以下标准：

- 任一本地 `ready` 书籍在断网下可完整阅读
- 阅读时切换章节不再触发格式 parser 解析正文
- 删除原始导入文件后，只要托管副本仍在，书籍仍可阅读
- `txt`、`epub`、`md`、`html` 完整打通导入、索引、阅读链路
- `epub` 可自动提取书名、作者、封面，并在有元数据时尽量提取简介
- `pdf` 明确仅支持文本型 PDF
- `mobi`、`azw`、`azw3` 明确仅支持无 DRM 文件
- 图文顺序以 `ReaderDocument` 为主表达，不依赖兼容字符串兜底

## 13. 最终建议

本地多格式阅读不应继续在旧的 `txt/epub` 懒解析路径上叠格式兼容，而应先完成一次架构收口。

推荐最终策略：

1. 先修正本地正文主路径：
   - `txt` 和 `epub` 在索引阶段完整落库
2. 再扩低风险格式：
   - `md`
   - `html`
3. 再补受限支持格式：
   - `pdf`（文本型）
   - `mobi`
   - `azw`
   - `azw3`（无 DRM）

如果后续要继续实施，本方案建议作为“本地阅读能力下一阶段主设计文档”使用，并在进入开发前拆分出：

- 详细任务清单
- 依赖选型结论
- 样本集和验收用例表
