# 缓存治理优化计划

创建日期：2026-06-02

状态：待执行

适用范围：移动端覆盖安装、长期使用、阅读链路缓存、分页缓存、封面缓存、正文内存缓存。

核心目标：缓存可以提升体验，但不能随着长期使用持续膨胀，也不能在启动、阅读、翻页主链路制造卡顿。

## 1. 背景与问题

当前项目已经有部分缓存治理能力，但还没有形成完整闭环。

- 章节正文 DB 缓存已有预算策略和 prune 能力。
- 分页布局磁盘缓存已有预算策略和 prune 能力。
- 封面磁盘缓存已有 compact 能力，但还没有接入统一治理。
- `AppCacheGovernanceService.enforceBudgets()` 已存在，但当前未查到启动或后台任务自动调用。
- `ChapterContentService._chapterCache` 当前是静态 `Map`，没有 TTL、容量上限和 LRU。
- iOS 删除 App 后重装仍可能保留 Keychain 登录态，这和缓存膨胀不是同一问题，但会让“重装后还是旧登录状态”更明显。

## 2. 优化原则

- [ ] 清理逻辑必须异步执行，不阻塞启动首帧、详情页打开、阅读页打开、正文渲染和翻页。
- [ ] 启动期清理必须放在首帧之后。
- [ ] 磁盘扫描必须节流，避免频繁全量扫目录。
- [ ] 缓存只允许删除可重建数据，不删除用户资产、登录数据、书架数据和阅读进度。
- [ ] 每类缓存同时考虑条数、体积和过期时间，不能只靠单一维度。
- [ ] 文档 checklist 必须随实现同步维护，完成一项打一项勾。

## 3. 建议预算

| 缓存类型 | 建议上限 | 建议 TTL | 清理触发时机 |
|---|---:|---:|---|
| 正文 DB | 3000 条 + 96MB | 45 天 | 启动首帧后 + App 后台 + 每 6 小时最多一次 |
| 分页磁盘 | 1200 条 + 24MB | 30 天 | 启动首帧后 + App 后台 |
| 封面磁盘 | 300 张 + 48MB | 30 天 | 启动首帧后 + 新封面写入后节流触发 |
| 正文内存 | 50 章 | 30 分钟 | 每次读写触发 LRU + TTL 淘汰 |
| 详情页内存 | 120 条 | 20 分钟 | 维持现有 |
| 分页内存 | 按设备 12 / 24 / 36 | 不设 TTL | 维持现有 LRU，后台或内存压力时可清 |
| EPUB archive | 4 个 | 不设 TTL | 维持现有 LRU |

## 4. 当前代码基线

- [x] 正文 DB 缓存表：`chapter_caches`。
- [x] 正文 DB 预算：`AppCacheBudgetPolicies.chapterCaches`，当前为 3000 条、96MB、45 天。
- [x] 分页磁盘预算：`AppCacheBudgetPolicies.paginationLayouts`，当前为 1200 条、24MB、30 天。
- [x] 封面磁盘预算：`AppCacheBudgetPolicies.coverImages`，当前为 300 张、48MB、30 天。
- [x] 统一治理服务：`AppCacheGovernanceService`。
- [x] 封面缓存压缩能力：`CoverImageDiskCache.compact()`。
- [x] 分页内存缓存：`ReaderPaginationCacheService`，默认 24 条，设备预算可调。
- [x] EPUB archive 内存缓存：当前最多 4 个。
- [ ] `AppCacheGovernanceService.enforceBudgets()` 自动触发链路尚未接入。
- [ ] 封面缓存 compact 尚未纳入 `AppCacheGovernanceService.enforceBudgets()`。
- [ ] 正文内存缓存 `_chapterCache` 尚无 LRU、TTL 和容量上限。

## 5. 阶段任务

### Phase 0：文档与基线

- [x] 梳理当前缓存类型、预算和缺口。
- [x] 固化本文档作为后续执行清单。
- [ ] 记录执行前缓存统计：正文 DB 条数和估算体积。
- [ ] 记录执行前缓存统计：分页磁盘条数和估算体积。
- [ ] 记录执行前缓存统计：封面磁盘张数和估算体积。

### Phase 1：统一治理闭环

- [ ] 在启动首帧后触发一次缓存治理。
- [ ] 增加治理节流，保证 6 小时内最多自动执行一次。
- [ ] App 进入后台时触发轻量治理。
- [ ] 治理过程不 await 到启动主链路。
- [ ] 治理失败只记录日志，不影响 App 正常使用。
- [ ] 补充治理日志：开始、结束、删除数量、耗时、失败原因。
- [ ] 验证启动首帧耗时不因治理变慢。

### Phase 2：封面缓存纳入治理

- [ ] 将 `CoverImageDiskCache.compact()` 接入 `AppCacheGovernanceService.enforceBudgets()`。
- [ ] 使用 `AppCacheBudgetPolicies.coverImages` 的 300 张、48MB、30 天预算。
- [ ] 新封面写入后只做节流触发，不每次同步全量 compact。
- [ ] 封面 compact 失败不影响封面显示和网络下载。
- [ ] 验证封面缓存超过条数或体积后会按最旧文件删除。

### Phase 3：正文内存缓存 LRU + TTL

- [ ] 将 `ChapterContentService._chapterCache` 从普通 `Map` 改成 LRU 结构。
- [ ] 默认最多保留 50 章。
- [ ] 每条正文内存缓存记录 `lastAccessAt`。
- [ ] 读取命中时刷新 LRU 顺序和访问时间。
- [ ] 写入时执行 TTL 淘汰。
- [ ] 写入时执行容量淘汰。
- [ ] TTL 默认 30 分钟。
- [ ] 保持 DB 正文缓存读取逻辑不变。
- [ ] 验证长时间连续阅读不会让内存缓存无限增长。

### Phase 4：后台与节流策略

- [ ] 新增缓存治理节流状态，优先使用轻量偏好或内存状态。
- [ ] 启动后治理和后台治理共享同一节流口径。
- [ ] 后台治理只执行可快速完成的预算压缩。
- [ ] 避免 App 频繁切前后台时重复扫磁盘。
- [ ] 记录上次治理时间和本次跳过原因。

### Phase 5：可观测与管理入口

- [ ] 在现有缓存管理或调试入口展示正文 DB 缓存条数和体积。
- [ ] 展示分页磁盘缓存条数和体积。
- [ ] 展示封面磁盘缓存张数和体积。
- [ ] 提供手动清理正文缓存入口。
- [ ] 提供手动清理分页缓存入口。
- [ ] 提供手动清理封面缓存入口。
- [ ] 手动清理必须明确提示只删除可重建缓存，不删除书架和阅读进度。

### Phase 6：回归验证

- [ ] `flutter analyze` 通过。
- [ ] 补充或更新缓存治理相关 unit test。
- [ ] iOS 模拟器启动验证：首帧不被缓存治理阻塞。
- [ ] 搜索 -> 详情 -> 开始阅读链路验证。
- [ ] 阅读页翻页验证：分页缓存命中和重建正常。
- [ ] 封面列表滚动验证：封面缓存清理后可重新下载。
- [ ] 覆盖安装验证：缓存预算不持续膨胀。
- [ ] 删除 App 后重装验证：普通缓存已清，Keychain 登录态另按认证策略处理。

## 6. 非目标

- [ ] 本计划不处理 Keychain 删除重装仍保留登录态的问题。
- [ ] 本计划不删除书架、本地图书、阅读进度、书签、用户主题资源和用户上传文件。
- [ ] 本计划不改变正文 DB 缓存的业务语义，只治理容量、体积和过期。
- [ ] 本计划不把分页内存缓存改成页面关闭即全清，避免损失短时间返回阅读页体验。

## 7. 风险与规避

- [ ] 风险：启动后立即扫磁盘导致低端设备卡顿。规避：首帧后异步执行，并加 6 小时节流。
- [ ] 风险：封面 compact 太频繁导致滚动时抖动。规避：新封面写入只触发节流治理。
- [ ] 风险：正文内存缓存过小导致反复解码 DB 内容。规避：先用 50 章，后续根据日志调整。
- [ ] 风险：误删用户资产。规避：只调用明确的缓存目录和缓存表删除 API。
- [ ] 风险：清理失败影响用户。规避：所有治理失败只记日志，不阻断 UI。
