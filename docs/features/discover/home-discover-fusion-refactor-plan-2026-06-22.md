# 首页 + 发现页融合改造方案

日期：2026-06-22

状态：完整改造方案，待评审

## 1. 背景

当前项目已经有书架、发现、搜索、详情、阅读器等主链路，但“首页”入口此前被移除，发现页目前更偏书源目录和分类入口。用户期望参考：

- `/Users/zhangyuanlong/Downloads/legado-own` 的现代发现页。
- `/Users/zhangyuanlong/Downloads/legado-with-MD3-main-xin` 的首页。

目标不是复制某一个项目，而是吸收两边优势，形成一个“首页 + 发现页”双页面结构：

- 首页负责快速消费内容、推荐、榜单、快捷入口。
- 发现页负责按书源深度探索、筛选、分类、源内搜索。

## 2. 参考结论

### 2.1 own 适合参考发现页

`legado-own` 的现代发现页核心优势：

- 顶部书源选择，保留当前选中书源记忆。
- 发现规则来自书源 `exploreKinds()`，不是写死频道。
- 一级分组、二级标签、筛选设置分层展示。
- `select`、`text`、`button` 等复杂规则进入设置弹窗，主界面保持轻。
- 标签过多时支持展开网格选择。
- 结果列表支持分页、下拉刷新、布局切换。
- 加载有版本号和 generation 控制，避免快速切换后旧请求覆盖新结果。
- 发现结果接入搜索结果、详情页、书架状态。

结论：own 更适合作为“发现页”的结构蓝本。

### 2.2 MD3-main-xin 适合参考首页

`legado-with-MD3-main-xin` 的首页核心优势：

- 首页是模块系统，而不是简单列表。
- 书源可通过 `homepageModules` 声明首页模块。
- 模块类型包括：
  - `banner`：横滑封面。
  - `ranking`：排行榜。
  - `gridRanking`：网格排行榜。
  - `grid`：固定行列推荐。
  - `card`：横向推荐卡。
  - `infiniteGrid`：无限网格。
  - `buttonGroup`：快捷分类按钮。
  - `waterfall`：瀑布流。
- 模块可以入库、排序、启用、屏蔽。
- 首页支持混合列表和分源 Tab。
- 模块标题可以跳转到对应发现列表。
- 书籍长按可预览，并支持加书架。

结论：MD3-main-xin 更适合作为“首页”的结构蓝本。

## 3. 产品边界

### 3.1 首页定位

首页是用户打开 App 后快速获得内容的地方。

首页应该承担：

- 推荐内容聚合。
- 今日/热门/榜单/新书等模块。
- 继续阅读、最近更新、书架动态的轻量入口。
- 快捷分类入口。
- 个性化或用户可配置模块。
- 长按预览、加书架、进入详情。
- 模块标题跳转到发现页或分类结果页。

首页不应该承担：

- 完整书源管理。
- 复杂规则调试。
- 大量筛选表单。
- 按书源逐项展开所有发现规则。
- 书架的完整管理职责。

### 3.2 发现页定位

发现页是用户主动找书、按书源探索的地方。

发现页应该承担：

- 选择书源。
- 查看书源发现分类。
- 分类筛选、文本筛选、按钮规则执行。
- 源内搜索。
- 分类分页列表。
- 列表、网格、紧凑网格布局切换。
- 登录当前书源、刷新书源规则。
- 处理书源失效、分类加载失败、规则为空等状态。

发现页不应该承担：

- 首页推荐流。
- 大量运营化模块。
- 书架管理。
- 统计报表。

### 3.3 书架定位

书架继续保持当前定位：

- 管理已加入书籍。
- 阅读进度、最近阅读、分类、标签。
- 本地书导入和阅读入口。

首页可以展示书架摘要，但不能替代书架。

## 4. 推荐信息架构

建议新安装或未配置用户的主导航默认形成：

1. 首页
2. 书架
3. 发现
4. 统计
5. 我的

统计入口保持现状，不纳入本次首页/发现页融合改造的变更范围。

### 4.1 导航个性化原则

新增“首页”后，不能强制所有用户启动进入首页。用户应该可以按自己的使用习惯调整主导航顺序，排序后的第一个可见入口就是启动入口。

必须支持：

- 拖动排序主导航：用户可以把书架、发现、首页或其他可见入口拖到第一位。
- 排序第一的可见入口就是启动入口，不再单独做一套启动页设置。
- 控制可见入口：延续当前项目已有策略，不在本方案里额外挪动统计入口。
- 恢复默认导航：一键回到推荐顺序：首页、书架、发现、统计、我的。
- 新旧偏好隔离：不能复活此前已删除的旧首页 key。

建议默认策略：

- 新用户或无显式配置用户：使用推荐顺序，首页排第一，因此默认进入首页。
- 已有用户升级：尽量尊重当前可见入口和排序，不强制跳到新首页。
- 如果用户此前已有显式导航配置，只插入新增首页入口，不重排其他现有入口。
- 如果用户显式隐藏某入口，升级后继续尊重隐藏配置。

## 5. 目标体验

### 5.1 首页目标体验

用户打开 App 后：

- 能看到继续阅读或最近更新入口。
- 能看到来自多个书源的精选模块。
- 能横滑浏览推荐。
- 能点模块标题进入更多。
- 能长按书籍预览。
- 能直接进入详情或加书架。
- 首页失败的单个模块不影响其他模块。

### 5.2 发现页目标体验

用户进入发现页后：

- 默认选中最近使用的可用书源。
- 书源切换流畅，不出现旧结果覆盖新结果。
- 分类标签清晰，复杂筛选不挤在主页面。
- 分类结果分页加载稳定。
- 能源内搜索。
- 能切换列表展示方式。
- 到详情、加书架、返回发现页的路径自然。

### 5.3 用户与设计简化审查

首页和发现页的底层业务会比较复杂，但不能把复杂度直接暴露给用户。设计目标是“默认可用、想改很快、高级能力藏得住”。

业务复杂点：

- 首页模块来源复杂：系统推荐、书源模块、用户手动模块、模块排序和启用状态。
- 发现页规则复杂：分类、筛选、文本输入、按钮动作、源内搜索、登录态。
- 主导航会新增首页，同时还要尊重老用户当前入口习惯。
- 首页、发现页、详情页、书架状态必须打通，不能各自孤立。

精简原则：

- 零配置可用：新用户或无配置用户打开 App 就能看到可用首页，不要求先选择书源或模块。
- 排序即启动：主导航拖拽排序后的第一个可见入口就是启动入口，不再提供第二套启动页设置。
- 首页模块默认智能生成：默认模块由系统和可用书源自动生成，用户只在想调整时进入管理。
- 发现页内完成发现设置：默认书源、分类、筛选都在发现页顶部和筛选弹层处理，不放到全局设置里。
- 高频操作外露，低频操作收纳：导航拖拽、模块开关、书源选择外露；手动模块、layoutConfig、自定义集放入高级管理。
- 失败局部化：某个首页模块失败只显示该模块错误，不让用户重新配置整页。

建议快速设置路径：

1. 调整启动入口：进入主导航编辑，拖动首页、书架、发现、统计、我的顺序；排第一的可见入口就是启动入口。
2. 调整首页内容：在首页进入模块管理，只做模块显示/隐藏、拖动排序、恢复默认；高级模块编辑放二级入口。
3. 调整发现偏好：在发现页顶部选择书源，系统自动记住；筛选只在当前书源和当前分类内生效。

不建议做：

- 不做单独的“默认启动页”设置页。
- 不做强制首启向导。
- 不要求用户先配置首页模块才能使用首页。
- 不把发现页的复杂筛选搬到全局设置。
- 不在本次首页/发现页方案里调整统计的产品位置。

## 6. 数据与能力设计

### 6.1 首页模块模型

建议新增首页模块模型，字段参考 MD3-main-xin，但按当前项目边界做 Flutter 侧落地。

建议字段：

- `id`：模块唯一标识。
- `sourceId`：来源书源。
- `moduleKey`：模块 key。
- `type`：模块类型。
- `title`：默认标题。
- `customTitle`：用户自定义标题。
- `url`：发现 URL 或模块 URL。
- `args`：临时变量或筛选参数。
- `layoutConfig`：布局配置 JSON。
- `isEnabled`：是否启用。
- `sortOrder`：排序。
- `createdByUser`：是否用户手动创建。
- `syncedAt`：同步时间。

首页模块能力建议一次性纳入本方案范围：

- 系统推荐模块。
- 从可用书源同步的首页模块。
- 用户启用/屏蔽和排序。
- 用户手动添加模块。
- 模块管理弹层。
- 首页混合列表和分源 Tab。
- 独立 layoutConfig。

### 6.2 首页模块类型

- `banner`
- `ranking`
- `grid`
- `card`
- `buttonGroup`
- `gridRanking`
- `infiniteGrid`
- `waterfall`

这些模块类型都属于本次完整目标。实施时可以按风险从低到高排序，但不拆成二期项目。

### 6.3 发现页分类模型

发现页应复用或扩展当前 `DiscoverSourceSummary` / `DiscoverSourceCategory` 能力。

建议分类模型能表达：

- `url` 分类。
- `select` 筛选。
- `text` 筛选。
- `button` 动作。
- 一级分组。
- 二级标签。
- 筛选默认值。
- 当前筛选值。

### 6.4 结果书籍模型

首页和发现页结果应尽量统一到同一类书籍展示模型，至少包含：

- 书名。
- 作者。
- 封面。
- 分类。
- 最新章节。
- 简介。
- 详情 URL。
- 来源书源。
- 是否已在书架。
- 是否同名同作者但不同来源。

### 6.5 导航偏好模型

新增首页后，需要把导航偏好升级成可排序模型，而不是只保存每个 Tab 是否可见。

建议模型：

- `items`：有序导航项列表。
- `visible`：每个导航项是否显示。
- `version`：偏好结构版本。
- `updatedAt`：最后更新时间。

建议导航项：

- `home`
- `bookshelf`
- `discover`
- `stats`
- `mine`

约束建议：

- `mine` 固定可见。
- 至少保留一个内容主入口：首页、书架、发现三者至少显示一个。
- 第一个可见入口就是启动入口。
- 旧首页偏好 key 只用于清理，不参与新首页恢复。
- 不单独保存启动页，避免排序和启动页两套状态互相冲突。

## 7. 技术边界

### 7.1 首页

首页建议新增独立 feature：

- `lib/features/home/domain`
- `lib/features/home/application`
- `lib/features/home/presentation`
- `lib/features/home/routes.dart`

首页不直接写书源解析逻辑，应通过 application service/use case 访问：

- 书源模块同步。
- 发现结果加载。
- 搜索结果缓存。
- 书架状态判断。

### 7.2 发现页

发现页继续放在：

- `lib/features/discover`

但需要逐步从“书源列表页”升级成：

- 现代发现首页。
- 发现结果页。
- 筛选弹层。
- 书源选择弹层。

### 7.3 导航

需要恢复新的首页入口，但不能恢复旧首页实现。

需要调整：

- Shell tab enum。
- Shell destination 列表。
- Router branch。
- 偏好存储。
- 图标配置。
- 首次启动默认入口。
- 主导航拖拽排序。
- 导航恢复默认配置。

注意：当前偏好里旧首页 key 被清理，新增首页时应使用新 key，避免复活旧数据。

## 9. 同一项目内的实施顺序建议

以下顺序只表示实现风险和依赖关系，不表示拆成二期或延期项目。

## 10. 风险点

- 首页恢复会影响现有 shell 导航，需要谨慎处理旧首页偏好。
- 首页新增后如果不支持拖拽排序，会打断习惯从书架或发现开始的老用户。
- 导航排序和入口可见性如果处理不当，容易出现第一项隐藏后启动空白或跳错页。
- 首页模块化如果一次做太完整，开发量会快速膨胀。
- 首页模块管理如果入口过深，会让用户误以为首页不可控。
- 首页模块管理如果入口过浅且选项过多，会让首页变成配置页。
- 发现页规则类型复杂，不能只支持 URL 分类，否则会丢书源能力。
- 发现页筛选如果全量外露，会让首屏看起来像规则调试器。
- 首页和发现页如果各自实现一套加载和书架状态，会产生重复 bug。
- 无限流、瀑布流容易引入滚动性能和分页状态问题。
- 书源失败需要局部失败，不应导致整页不可用。

## 11. 推荐落地路径

本方案按一次完整项目落地，不拆二期项目。阶段只表示实施顺序，不表示功能延后到另一个项目。

建议先打通基础闭环：

- 首页入口。
- 导航拖拽排序和首项启动。
- 首页基础模块。
- 首页到详情/书架。
- 发现页现代基础结构。
- 发现页分类和分页。
- 首页跳发现页。

随后在同一项目内补齐完整能力：

- 模块管理。
- 分源 Tab。
- layoutConfig。
- 瀑布流和无限网格。

这样可以控制实现风险，但最终验收以完整目标为准，不以“只完成基础闭环”作为上线口径。
