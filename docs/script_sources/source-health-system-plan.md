## 1. 目标

把下面这些能力统一到同一套“源健康系统”里：

- 搜索调度
- 手动换源
- 自动换源
- 书源列表状态展示
- 源检测
- 建议停用 / 自动停用

一句话：

- 不再让“搜索失败记录”“换源排序”“源检测结果”“停用判断”各自维护一套状态
- 改成一份统一的源健康事实，被不同功能消费

## 2. 为什么要单独做这份规划

当前我们已经做完了搜索运行时的：

- 执行画像
- 预算调度
- 取消链路
- 运行时复用
- 动态画像与短时熔断

但这些能力现在仍然主要服务：

- `搜索`
- `手动换源`
- `自动换源`

如果后面要做：

- 源列表状态标签
- 单源检测 / 批量检测
- 自动停用

那就必须把“源健康”抽象成正式能力，否则会出现：

- 搜索里有一套健康判断
- 换源里有一套风险判断
- 检测页再做一套可用性判断
- 停用策略再做第四套规则

这会重复，也会彼此冲突。

## 3. 核心判断

源健康系统的本质不是“打分面板”，而是“统一事实层”。

正确的分层应该是：

1. 运行时产生事实
2. 健康层汇总事实
3. 业务层消费健康状态

不是反过来从 UI 侧零散推导。

## 4. 统一模型

建议新增一个统一的健康状态模型，例如：

```dart
class SourceHealthSnapshot {
  final String sourceId;
  final SourceHealthLevel level;
  final bool enabled;
  final bool coolingDown;
  final DateTime? cooldownUntil;
  final int totalSuccesses;
  final int totalFailures;
  final int consecutiveFailures;
  final int browserRiskCount;
  final int challengeCount;
  final int timeoutCount;
  final Duration? avgSearchLatency;
  final Duration? avgDetailLatency;
  final DateTime? lastSuccessAt;
  final DateTime? lastFailureAt;
  final String? lastFailureReason;
}
```

建议的健康等级：

```dart
enum SourceHealthLevel {
  healthy,
  warning,
  risky,
  unavailable,
}
```

说明：

- `healthy`：最近稳定
- `warning`：有失败，但还不影响主流程
- `risky`：需要降权、限流或建议用户关注
- `unavailable`：近期连续失败，不建议参与搜索/换源

## 5. 事实来源

健康系统不应该只看“搜索成功没成功”，而应该统一吸收多类运行事实。

### 5.1 搜索链

- 搜索成功次数
- 搜索失败次数
- 连续失败次数
- 平均耗时
- 是否触发 browser/challenge
- 是否被熔断 / 冷却

### 5.2 换源链

- 手动换源成功率
- 自动换源成功率
- 候选命中率
- 被评分降权/加权的记录

### 5.3 检测链

- 单次检测成功/失败
- 失败原因分类
- 检测耗时
- 最近检测时间

### 5.4 用户动作

- 用户手动启用/停用
- 用户手动推荐/降权
- 用户忽略风险提示

## 6. 消费场景

### 6.1 搜索

搜索消费健康状态的方式：

- 健康源优先
- 风险源降权
- 冷却中的源跳过
- 不可用源默认不参与，除非用户显式指定

### 6.2 手动换源

手动换源消费健康状态的方式：

- 候选排序里加入健康权重
- 对高风险源打标签，但不强制隐藏
- 用户仍可主动选中高风险源

### 6.3 自动换源

自动换源消费健康状态的方式：

- 只尝试稳定源
- 跳过需要交互 challenge 的高风险源
- 跳过冷却中/不可用源

### 6.4 书源列表

书源列表消费健康状态的方式：

- 展示状态标签
- 展示最近一次失败原因
- 展示冷却时间
- 展示建议动作，例如“建议检测”“建议停用”

### 6.5 源检测

源检测消费健康状态的方式：

- 以当前健康状态决定检测优先级
- 检测后回写健康状态
- 支持批量检测时跳过短时冷却源

### 6.6 停用策略

停用能力消费健康状态的方式：

- 先给建议
- 再提供用户确认停用
- 最后才考虑自动停用

## 7. 源检测设计

源检测应该是“健康系统的主动探针”，而不是孤立功能。

### 7.1 检测入口

建议至少提供两类入口：

- 单源检测
  入口挂在书源列表单项的更多菜单中
- 批量检测
  入口挂在书源列表页工具栏或批量操作模式中

后续可选补充：

- 最近失败源快速检测
- 当前启用源批量检测
- 冷却中源重新检测

### 7.2 检测对象范围

批量检测不要默认把所有源全量打一遍。

建议支持这些范围：

1. `当前选中源`
2. `当前启用源`
3. `当前筛选结果`
4. `最近失败源`
5. `冷却中源`

默认推荐：

- 用户从列表页点“批量检测”时，默认选“当前启用源”
- 如果用户已经做了分组或搜索筛选，允许直接检测“当前筛选结果”

建议检测模式：

- 单源检测
- 批量检测
- 最近失败源快速检测
- 当前启用源定时检测

建议检测级别：

1. `searchOnly`
   只测 `search()`
2. `searchAndDetail`
   测 `search() + detail()`
3. `fullReadPath`
   测 `search() + detail() + chapters() + content()`

默认建议：

- 源列表里的快速检测只跑 `searchOnly`
- 用户显式深度检测时再跑更重路径

### 7.3 检测结果分级

建议把检测结果标准化成统一等级，而不是只给一段错误文本：

```dart
enum SourceCheckStatus {
  healthy,
  warning,
  failed,
  skipped,
}
```

含义建议：

- `healthy`
  目标步骤全部通过
- `warning`
  主路径可用，但有高风险迹象
  例如：
  - 耗时过高
  - 需要 browser/challenge
  - 章节/正文路径不稳定
- `failed`
  检测目标步骤未通过
- `skipped`
  因为冷却、禁交互、用户取消、预算不足等原因未执行

每个检测结果建议至少包含：

- `sourceId`
- `status`
- `checkedLevel`
- `duration`
- `stepReached`
- `message`
- `needsBrowser`
- `canAutoDisable`
- `canBatchDelete`

### 7.4 单源检测交互建议

单源检测的目标不是“跑很重”，而是“快速判断这个源当前值不值得继续留着”。

建议默认流程：

1. 用户在书源列表点单源“检测”
2. 默认执行 `searchOnly`
3. 返回状态卡片：
   - 健康
   - 风险
   - 失败
   - 跳过
4. 如果 `searchOnly` 通过，再允许用户继续点“深度检测”

单源检测结果页建议展示：

- 最近失败原因
- 最近成功时间
- 本次耗时
- 是否触发 browser/challenge
- 建议动作：
  - 重新检测
  - 停用
  - 删除
  - 查看调试日志

### 7.5 批量检测交互建议

批量检测的目标不是一次性给出完美报告，而是让用户快速筛出有问题的源。

建议批量检测页至少有：

- 当前总数
- 已完成数
- 通过数
- 风险数
- 失败数
- 跳过数

并支持结果分组：

- 健康
- 风险
- 失败
- 跳过

建议默认只展示失败与风险源，健康源折叠。

### 7.6 批量操作建议

你提到“检测出来有问题的源，用户可以批量删除”，这个是合理需求，但建议操作层级要分开：

第一优先级：

- 批量停用

第二优先级：

- 批量重新检测

第三优先级：

- 批量删除

原因：

- 失败不一定代表永久无效
- 很多源只是站点临时波动、验证码、网络问题
- 批量删除误伤成本很高

所以默认建议是：

- 对 `failed / risky` 源先支持批量停用
- 删除作为二次确认后的高级操作

批量删除建议加约束：

- 只允许对当前检测结果列表里的失败源执行
- 必须二次确认
- 删除前明确提示：
  - 将删除源配置本身
  - 不会自动删除用户已有书架记录
  - 已删除源后续不能参与搜索/换源

### 7.7 与健康系统的关系

检测结果不是独立数据，它必须回写健康状态：

- `healthy`：清空连续失败、解除冷却
- `warning`：提升风险权重，但不进入不可用
- `failed`：增加失败计数，满足条件进入冷却
- `skipped`：通常不算失败，但要记录原因

这意味着：

- 检测页不是只展示一次结果
- 它会直接影响后续搜索、换源和源列表状态

## 8. 停用策略建议

自动停用一定要保守，建议三层策略：

### 8.1 第一层：标记

- 只展示风险
- 不自动改源状态

### 8.2 第二层：建议停用

- 连续多次失败
- 长期不可用
- 高风险 challenge 且不可恢复

此时只提示，不直接停用。

### 8.3 第三层：自动停用

只建议在满足严格条件时开启，例如：

- 连续 N 次检测失败
- 最近 M 天没有一次成功
- 用户已经打开“允许自动停用高风险源”

默认不建议直接启用自动停用。

### 8.4 关于自动删除

不建议做“自动删除”。

原因：

- 删除是不可逆的管理动作
- 源失败可能只是临时状态
- 用户通常更容易接受“自动停用”，不容易接受“自动删除”

建议规则：

- 自动停用可以规划
- 自动删除不建议规划
- 删除始终保留为用户主动确认操作

## 9. 持久化建议

健康状态必须持久化，否则每次启动都从零开始。

建议存储字段：

- `sourceId`
- `level`
- `cooldownUntil`
- `totalSuccesses`
- `totalFailures`
- `consecutiveFailures`
- `browserRiskCount`
- `challengeCount`
- `timeoutCount`
- `avgSearchLatencyMs`
- `avgDetailLatencyMs`
- `lastSuccessAt`
- `lastFailureAt`
- `lastFailureReason`
- `userDisabled`
- `userScoreAdjustment`

## 10. 衰减规则

持久化以后必须有衰减，不然旧问题会永久污染现状。

建议：

- `consecutiveFailures` 在一次成功后清零
- `cooldownUntil` 到期后自动失效
- `browserRiskCount / challengeCount / timeoutCount` 采用时间衰减
- `avgLatency` 用滑动窗口或指数平均
- `lastFailureReason` 只保留最近一次

## 11. 与当前搜索运行时的关系

当前搜索运行时已经提供了：

- 画像
- 熔断
- 冷却
- 预算调度

源健康系统不是要替代这些，而是：

- 把这些能力从“搜索内部状态”提升为“全局可消费状态”

也就是说：

- 搜索运行时是事实生产者
- 源健康系统是事实汇总层
- 源列表 / 检测 / 停用是事实消费者
