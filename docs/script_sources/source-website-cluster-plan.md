# 书源网站关联与重复源治理计划

更新时间：2026-04-05

当前说明：

- 本文讨论的是“同站书源很多、搜索并发会互相影响、列表又难清理”这一类问题。
- 本文只针对脚本源，不涉及旧规则 JSON。
- 本文不主张把两个导入文件合并成一条书源记录。

## 0. 问题定义

当前真实问题不是：

- 单个书源一定有 bug

而是：

- 用户会导入多个指向同一网站的书源
- 这些书源在存储层是独立源
- 但搜索时宿主会把它们当作完全无关的独立任务并发执行
- 同站状态、cookie、challenge、返回页面在并发下互相影响
- 最终导致搜索不稳定，严重时甚至触发宿主崩溃

一句话总结：

- 源实例必须独立
- 同站关系必须被识别
- 调度要按同站关系做保护

## 1. 设计原则

这是本文最重要的三条原则。

### 1.1 不合并用户导入的源

用户导入两个文件，即使它们：

- 网站一样
- 规则很像
- 甚至几乎完全重复

也仍然是两条独立书源记录。

宿主不能因为“看起来像重复源”就把它们合并成一条。

原因：

- 用户可能故意保留两个版本
- 两个源可能有不同搜索策略
- 两个源的 cookie / session / cache 必须独立

### 1.2 同站关系只用于“关联”和“调度保护”

同站关系的作用应该是：

- UI 上提示“这是同一个网站的多个源”
- 搜索时避免同站无脑并发
- 帮助用户清理重复网站源

同站关系不应该用于：

- 合并源记录
- 共享 cookie
- 共享 session
- 共享源级评分

### 1.3 搜索层不能只按纯域名一刀切

同一个网站下，可能存在多种搜索变体，例如：

- 按书名搜索
- 按作者搜索
- 按站内编号搜索

所以：

- 列表层可以按网站聚合
- 搜索调度层不能简单只看网站
- 后续需要引入“搜索变体”概念

## 2. 当前逻辑梳理

### 2.1 现有 `group` 的定位

当前书源页右上角“分组”来自：

- `ScriptSource.group`

这个字段来自：

- 书源 `meta.group`

所以当前 `group` 是：

- 人工分组
- 作者分组
- 来源分组

它不是网站分组。

### 2.2 当前数据层的问题

当前宿主之前缺少网站级元数据。

后来已经补进了：

- `primaryHost`
- `registrableDomain`
- `clusterKey`

这些字段现在已经能在保存书源时从：

- `homepage`
- `domains`

自动提取。

这意味着：

- 网站关联的底座已经有了
- 现在差的是 UI 和调度如何正确消费它

## 3. 正确的数据分层

最优解不是“只加一个 clusterKey”，而是把身份分层说清楚。

### 3.1 源实例身份

按 `sourceId`

负责：

- 书源编辑
- 启用 / 停用
- 删除
- 源级健康状态
- 源级评分
- cookie / session / cache

这一层必须独立。

### 3.2 网站关联身份

按 `websiteGroupKey`

v1 可以直接等于：

- `registrableDomain`

负责：

- 识别同站源
- 列表筛选重复网站源
- 搜索时同站限流 / 串行
- 站点级运行时状态

### 3.3 搜索变体身份

这一层是后续搜索调度真正需要补的。

例如：

- `title`
- `author`
- `mixed`

最终可以组合成：

- `searchGroupKey = websiteGroupKey + ':' + searchVariantKey`

这样：

- 列表层仍按网站聚合
- 搜索层则能区分“同站但不同搜索策略”

## 4. 当前阶段的最优 UI 方案

这里要修正之前的方向。

最优解不是：

- 普通列表 / 按网站聚合 双模式切换

而是：

- 保持一个列表
- 增加“重复网站源”相关筛选
- 在列表项上直接展示网站信息

这样更直观，也更不破坏现有交互。

### 4.1 保持一个列表

继续保留现有：

- 搜索
- 排序
- group 过滤

不引入第二套列表模式心智。

### 4.2 列表项增强

每条书源建议直接展示：

- `站点: sudugu.org`
- `同站 8 个`
- `推荐保留`
- `失败原因`
- `自动停用原因`

这样用户不切模式也能看出重复关系。

### 4.3 复用现有分组入口

不额外在页面里增加一排网站筛选 UI。

直接复用右上角“分组”入口，新增一个系统分组项：

- `重复源`

判定规则：

- 同一网站组内源数量 `>= 2` 时，视为重复网站源

这样用户仍然只面对一个列表，只是多了一个最常用的“重复源”筛选入口。

## 5. 当前阶段的最优调度方案

### 5.1 列表层

按 `websiteGroupKey` 标记同站关系。

目的：

- 让用户识别重复网站源
- 让用户自行决定是否清理

### 5.2 搜索层

短期内最保守的做法：

- 同站源不要同时并发打站

但这里不能直接把同站源当成同一个源。

正确理解是：

- 源实例仍然独立
- 只是调度上要更保守

### 5.3 未来搜索变体支持

对于“同站但一个搜书名、一个搜作者”的源：

- UI 上它们仍属于同站组
- 但搜索调度里不能简单只按网站去重

所以后续最优做法是：

1. 先按网站组
2. 再按搜索变体组
3. 最终调度按 `searchGroupKey`

## 6. 推荐落地顺序

### 阶段 A：网站元数据持久化

- [x] 为 `ScriptSource` 增加 `primaryHost / registrableDomain / clusterKey`
- [x] 保存书源时自动提取并落库
- [ ] 历史数据提供一次补齐逻辑

### 阶段 B：单列表增强与重复网站源筛选

- [x] 列表项显示 `站点 / 同站数量 / 推荐保留`
- [x] 右上角“分组”支持 `重复源`
- [ ] 支持 `仅看建议清理`
- [ ] 支持 `仅看推荐保留`

### 阶段 C：重复源治理动作

- [x] 支持“停用同站其余源”
- [ ] 支持“删除已停用源”
- [ ] 支持“仅删非推荐保留源”的保护策略

### 阶段 D：搜索调度联动

- [ ] 搜索先按 `websiteGroupKey` 做同站保护
- [ ] 同站默认串行或限流
- [ ] 引入 `searchVariantKey`
- [ ] 最终形成 `searchGroupKey`

## 7. 当前阶段判断

当前最优解已经不是“做一个聚合视图”，而是：

- 一个列表
- 一层网站关联元数据
- 一组重复网站源筛选
- 一套更保守的同站搜索调度

最终一句话：

- **源实例独立**
- **网站关系可见**
- **调度按关系保护**
