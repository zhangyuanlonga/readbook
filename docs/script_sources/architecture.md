# 小说聚合平台总体架构

## 1. 目标

项目目标不是单纯做一个“能执行 JS 的 App”，而是做一个：
- 支持多站点聚合搜索的小说客户端
- 支持社区化扩展书源的运行平台
- 支持 API、HTML、浏览器验证混合流程的宿主系统

核心产品特征：
- 用户输入关键词后，并发查询多个书源
- 每个书源都可以有自己的搜索、详情、目录、正文逻辑
- 某些书源可以只走 API
- 某些书源可以请求 HTML 再解析
- 某些书源可以在流程中途切换到浏览器环境，让用户手动完成人机验证
- 某些书源也可以在正式步骤前先执行初始化动作，例如取 token、检查登录态或先让用户登录

## 2. 核心设计原则

### 2.1 源作者写“站点适配逻辑”，宿主掌控执行权

源脚本可以自由组合宿主能力：
- `ctx.http.request(...)`
- `ctx.html.parse(...)`
- `ctx.browser.challenge(...)`
- `ctx.browser.eval(...)`

但源脚本不能直接操控 Flutter 组件，也不能越过宿主直接访问系统能力。

### 2.2 不使用单一全局源类型

一个源不应该被粗暴标记为：
- `api 源`
- `html 源`
- `browser 源`

真实场景里，一个源往往是混合的：
- 搜索走 API
- 详情走 HTML
- 正文因为风控需要浏览器验证

因此执行策略必须按步骤定义。

### 2.3 浏览器能力只做兜底，不做默认主路

浏览器环境更接近真实页面，但代价也更高：
- 更重
- 并发能力更差
- 更依赖页面状态和用户介入

因此默认主路应是宿主 HTTP/HTML 能力，浏览器能力只在这些场景启用：
- 人机验证
- 验证码
- 真实 DOM 依赖
- 动态页面脚本执行
- 必须继承浏览器 Cookie/Storage 的流程

## 3. 三层执行架构

## 3.1 宿主请求层

职责：
- 统一 HTTP 请求
- 管理超时、重试、Header、UA、Cookie
- 统一编码处理
- 做基础缓存
- 做响应标准化

这一层是大多数书源的主执行层。

## 3.2 书源脚本层

职责：
- 定义书源元信息
- 定义可选前置步骤
- 定义搜索、详情、目录、正文逻辑
- 组合调用宿主能力
- 维护站点级上下文数据

书源对外以单个 `.js` 文件分发。

## 3.3 浏览器交互层

职责：
- 加载目标页面
- 执行页面 JS
- 让用户手动处理验证码或验证流程
- 回传 Cookie、验证结果或 DOM 提取结果

这一层必须和 Session 体系打通。

## 4. 核心模块

### 4.1 SourceRegistry

职责：
- 加载本地书源
- 管理启停状态
- 做源版本升级和冲突检测

### 4.2 SourceExecutor

职责：
- 执行某个源的 `search/detail/chapters/content`
- 给源脚本注入 `ctx`
- 负责方法超时、错误捕获、能力白名单控制

### 4.3 RequestEngine

职责：
- 封装统一 `ctx.http.request`
- 会话复用
- 挑战页检测
- 重定向、编码、压缩、重试处理

### 4.4 SessionManager

职责：
- 按源维护 Session
- 管理 Cookie、User-Agent、默认 Header
- 跟浏览器会话同步
- 支持“验证前”和“验证后”状态切换

### 4.5 CacheManager

职责：
- 管理搜索、详情、目录、正文的业务缓存
- 降低重复请求成本
- 提供按源、按书、按步骤的清理能力

边界：
- SessionManager 管“会话状态”
- CacheManager 管“业务结果”

### 4.6 ChallengeManager

职责：
- 管理 `challenge` 生命周期
- 调起浏览器验证页
- 检测验证成功
- 恢复挂起任务

### 4.7 BrowserRuntime

职责：
- 承载浏览器模式
- 运行 DOM / 页面脚本
- 执行 `ctx.browser.eval`
- 执行 `ctx.browser.challenge`

### 4.8 SearchAggregator

职责：
- 并发搜索多个源
- 流式回传结果
- 去重和合并
- 上报每个源当前状态

## 5. 标准业务链路

### 5.1 搜索链路

1. 用户输入关键词
2. SearchAggregator 选出已启用源
3. 按并发上限调度多个源
4. 优先检查搜索缓存
5. 每个源执行 `search(ctx, keyword)`
6. SearchAggregator 流式接收 `Book[]`
7. 做标准化、去重、来源合并
8. UI 实时展示部分结果和源状态

### 5.2 详情链路

1. 用户点击一本书
2. 根据 `sourceId` 找到对应书源
3. 优先检查详情缓存
4. 执行 `detail(ctx, book)`
4. 返回增强后的 `Book`
5. 详情页基于标准字段渲染

### 5.3 目录链路

1. 进入目录页
2. 优先检查目录缓存
3. 执行 `chapters(ctx, book)`
3. 返回 `Chapter[]`
4. 缓存目录数据

### 5.4 正文链路

1. 用户点击章节
2. 优先检查正文缓存
3. 执行 `content(ctx, book, chapter)`
3. 返回 `Content`
4. Reader 页面渲染正文

## 6. 链式上下文设计

源步骤不是彼此独立的。

例如：
- 搜索结果里的 `detailUrl` 会被详情页继续使用
- 详情页拿到的 `catalogUrl` 会被目录接口继续使用
- 某些隐藏参数、token、csrf 会一路传递到正文请求

因此数据对象设计必须支持“标准字段 + 站点私有上下文”。

推荐做法：
- 标准字段直接放在 `Book/Chapter/Content`
- 站点内部上下文统一放在 `extra`
- 调试信息可选放在 `debug`
- 跨步骤共享的会话级数据统一放在 `ctx.session`

不要把整份原始 HTML 默认塞进标准对象。

## 7. 书源执行策略

`v1` 不要求源作者预先声明 `execution`。

原因：
- 很多源作者在编写时并不能提前准确判断每一步最终会走 `http` 还是 `browser`
- 同一个流程里，某一步可能先走普通请求，中途再因为 challenge 升级到浏览器
- 强制写 `execution` 往往会变成维护负担

因此在 `v1` 里，执行策略由这三部分共同决定：
- 源脚本直接调用的宿主能力
- 宿主对响应内容的自动识别
- challenge / browser 步骤对当前会话状态的影响

也就是说：
- 源调用 `ctx.http.request(...)`，就先走宿主请求层
- 源调用 `ctx.browser.challenge(...)`，就进入浏览器验证流程
- 源调用 `ctx.browser.eval(...)`，就进入真实页面执行流程

宿主负责理解这些调用并执行，而不是要求源作者先写一份静态执行声明。

## 7.1 前置步骤

`v1` 支持一个可选前置钩子：

```js
async init(ctx, task) {}
```

适用场景：
- 先请求自己的服务端拿必要参数
- 先检查某个源的登录态
- 正式请求站点前先打开浏览器让用户登录
- 初始化公共 token、签名、Cookie、Header

推荐原则：
- `init` 只做初始化动作
- 业务解析逻辑仍然放在 `search/detail/chapters/content`
- 需要跨步骤复用的数据优先写入 `ctx.session`

## 8. 验证码 / 人机验证设计

设计目标：
- 不因为单个源需要验证，就阻塞整个搜索
- 可以在中途挂起当前源任务
- 用户完成验证后自动恢复

推荐流程：
1. 书源请求某页
2. 宿主或书源识别出 challenge
3. 源脚本调用 `ctx.browser.challenge(...)`
4. 宿主打开验证页
5. 用户手动验证
6. SessionManager 同步验证态
7. 原任务恢复执行

## 9. 为什么不用“纯浏览器”或“纯脚本引擎”

### 9.1 纯浏览器方案的问题

- 并发搜索多个源成本太高
- 内存占用更重
- 复杂度更高
- 不适合作为主执行路径

### 9.2 纯脚本引擎方案的问题

- 缺乏真实 DOM 和浏览器上下文
- 复杂站点、人机验证、动态页面支持不足
- 最后还是要靠宿主不断补能力

最佳方案是：
- 普通请求走宿主 HTTP
- 复杂流程升级到浏览器

## 10. 合规与风险

该类项目需要单独评估：
- 版权风险
- 站点服务条款
- 反爬与风控策略
- 源分发安全

架构层面至少应预留：
- 源黑名单 / 禁用机制
- 远程下线某个源的能力
- 版本签名或可信来源管理

## 11. 第一阶段建议落地顺序

1. 完成 `v1` 书源规范
2. 实现 `RequestEngine`
3. 实现 `SourceExecutor`
4. 完成一个 API 型 demo 源
5. 完成一个 HTML 型 demo 源
6. 实现 `ChallengeManager + BrowserRuntime`
7. 接入聚合搜索 UI
