# 第二阶段：Browser / Cookie / Cache 设计说明

这份文档只解释第二阶段为什么优先做 `browser / cookie / cache`，不再重复作者手册和 API 参考内容。

如果你是第一次写源，请先看：

- [官方书源编写手册](./official-source-author-guide.md)
- [书源规范 v1](./source-spec-v1.md)
- [宿主运行时 API](./runtime-ctx-api.md)

---

## 1. 第二阶段主线

第二阶段的目标不是“补一个登录模块”，而是补齐一类通用宿主能力：

- 普通 `http + html` 走不通时，规则仍能继续
- 规则可以进入真实浏览器上下文
- 浏览器态与请求态可以协同

因此当前主线只有三项：

1. `browser`
2. `cookie`
3. `cache`

---

## 2. 核心设计原则

### 2.1 做通用能力，不做站点专用 hack

平台应提供通用 `browser / cookie / cache` 能力，让规则自行组合。  
不应为了个别站点在核心模型里加入专用字段或专用流程。

### 2.2 规则负责表达，宿主负责执行

规则脚本表达“要做什么”，例如：

- 打开浏览器
- 等待 URL 变化
- 执行页面 JS
- 读取 cookie 或 cache

宿主负责真正执行这些动作，并维护运行时状态。

### 2.3 Browser 不等于 Login

当前阶段最重要的边界就是：

- `browser` 是浏览器上下文能力
- `login` 不是当前核心抽象

`browser` 除了登录，还服务于：

- challenge / Cloudflare
- 页面跳转等待
- DOM 抓取
- storage 读取
- 页面内 JS 取值

### 2.4 能力解耦，避免一个方法包办所有事

浏览器类能力如果把“打开页面、等待用户操作、同步 cookie、同步 HTML、同步 storage、恢复执行”全部塞进一个方法，会带来两个问题：

- 规则作者不知道宿主偷偷做了什么
- 调试时很难定位是哪一步失败

因此当前设计应保持拆分：

- `challenge` 负责 challenge
- `eval` 负责页面执行
- `cookie` 负责 cookie
- `cache` 负责 cache
- 页面快照按需获取

---

## 3. 当前边界结论

这一阶段优先保证的是：

- 浏览器能打开
- challenge 能完成
- cookie 能协同
- cache 能协同
- 规则能继续执行

当前不以这些为默认目标：

- 自动同步完整 HTML
- 自动同步完整 storage
- 自动推断登录态
- 自动把 browser 当成登录模块
