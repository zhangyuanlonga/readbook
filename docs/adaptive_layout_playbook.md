# 自适应落地策略

更新时间：2026-04-08  
用途：把 Flutter 官方推荐、国内常用做法、当前项目代码现状和后续改造策略统一成一份可执行文档。  
适用范围：主壳层、书架、搜索、书源、详情、阅读设置弹层。

## 1. 文档目标

本文件回答 4 个问题：

1. Flutter 官方更推荐哪些自适应手段
2. 国内项目里最常见的自适应做法是什么
3. 当前项目更适合哪种组合方案
4. 后续页面应该按什么标准判断“用重排”还是“用等比缩放”

## 2. 官方推荐与国内常用做法

## 2.1 Flutter 官方推荐

Flutter 官方整体更推荐：

- 页面和组件优先基于约束做判断
- 页面级优先使用 `LayoutBuilder`
- 组件级优先使用 `constraints.maxWidth`
- 顶层可以使用基于逻辑宽度的断点
- 自适应不只看屏幕，还要看输入方式、方向、可用空间

这类思路的核心是：

- responsive：根据空间变化布局
- adaptive：根据设备能力和场景变化交互与结构

对当前项目最有用的官方结论是：

- 页面骨架不要只看整屏宽度
- 组件内部优先看当前可用宽度
- 大屏适配应先解决结构问题，而不是只缩放

## 2.2 国内项目常用做法

国内 Flutter 项目常见是两派混用：

### A. 断点 / 约束派

常用工具：

- `LayoutBuilder`
- `MediaQuery`
- `shortestSide`
- `ConstrainedBox`
- 自定义 `AppLayout`
- `responsive_framework`

优点：

- 大屏适配更自然
- 能做真正布局重排
- 更适合手机、平板、桌面统一设计

缺点：

- 代码量更大
- 需要持续维护页面结构

### B. 设计稿缩放派

常用工具：

- `flutter_screenutil`
- `px -> .w / .h / .sp`

优点：

- 还原设计稿快
- 小团队开发效率高
- 手机端纯视觉统一时省力

缺点：

- 大屏体验通常一般
- 不能替代真正布局重排
- 很容易把“原本就不合理的密度”整体放大或缩小

## 2.3 对当前项目的适配结论

当前项目已经具备：

- 全局断点
- 页面级限宽
- `NavigationRail` 切换
- 局部网格列数逻辑

所以项目当前最适合的方向不是：

- 纯设计稿缩放

而是：

- **约束驱动布局**
- **页面级重排**
- **复杂控制面板局部等比缩放**

一句话：

**当前项目更适合“官方约束方案为主，国内常用缩放方案为辅”的混合模式。**

## 3. 项目统一口径

## 3.1 判断顺序

后续页面和组件统一按这个顺序判断：

1. **先看当前容器宽度**
   适用于页面主体、卡片区、宫格区、弹层内容区

2. **再看页面级逻辑宽度**
   适用于页面骨架、双栏、侧栏、rail 切换

3. **最后才考虑等比缩放**
   适用于复杂控制面板，不适用于信息流页面

## 3.2 统一指标

后续项目内允许使用的主要判断指标：

- `constraints.maxWidth`
- `AppLayout.widthBucketFor(width)`
- `AppLayout.pageContentMaxWidth()`
- `AppLayout.sheetHeightFactor()`
- `MediaQuery.sizeOf(context).width`
- `MediaQuery.orientation`
- `MediaQuery.textScalerOf(context)`

不建议作为主判断依据的做法：

- 只按整屏宽度写死组件结构
- 全页面依赖设计稿缩放
- 仅靠 `maxWidth` 当作“大屏适配完成”

## 3.3 统一断点角色

当前项目保留这些断点角色：

- `<= 360`
  小屏特判，只用于压缩密度与最小可用性兜底

- `390`
  大号手机起点，适合做手机内部密度差异，不作为大屏布局主分界

- `480`
  超大手机 / 横屏手机过渡带，适合做手机内部控件比例调整

- `600`
  中屏布局起点，适合切 `NavigationRail`、双栏和侧栏

- `840`
  扩展布局起点，适合稳定大屏布局

解释：

- `600 / 840` 属于更强的结构断点
- `390 / 480` 更适合做手机内部分层
- 不要把 `390` 和 `600 / 840` 当作同级页面结构断点来理解

## 4. 页面类型与推荐策略

## 4.1 信息流页面

适用页面：

- 书架
- 搜索
- 书源
- 书籍详情

推荐策略：

- 以**布局重排**为主
- 不以等比缩放为主策略

原因：

- 用户核心感知是信息组织方式
- 大屏时更该提升信息密度与层级，而不是把手机 UI 放大

落地方式：

- 列数变化
- 主次区域分栏
- 列表与筛选分栏
- 内容卡片布局变化
- 局部信息并列显示

## 4.2 控制面板页面

适用区域：

- 阅读设置弹层
- 小型工具面板
- 控制项密集的操作面板

推荐策略：

- **局部重排 + 小范围等比缩放**

原因：

- 用户对这类区域的预期是“同一套控件”
- 不一定需要彻底换布局
- 但必须解决固定尺寸导致的挤压问题

落地方式：

- 保留结构
- 用面板宽度算一个缩放因子
- 缩放圆角、图标、胶囊高度、间距、背景卡片尺寸
- 文本只做小幅缩放
- 控件组在必要时改列数

## 5. 当前项目的页面级建议

## 5.1 书源页

现状：

- 已有限宽保护
- 主列表仍偏单列手机结构

建议：

- `600+` 引入筛选侧栏或双栏信息结构
- 列表项内部增加大屏信息展开
- 搜索与过滤区域不再完全堆叠

主策略：

- **重排**

## 5.2 书架页

现状：

- 有部分列数逻辑
- 页面骨架整体仍偏手机

建议：

- 主流大屏上强化信息分层
- 顶部筛选、标签、摘要区与内容区关系重做
- 列表与网格模式分别补大屏样式

主策略：

- **重排**

## 5.3 搜索页

现状：

- 已有限宽
- 主结果区仍偏单列信息流

建议：

- `600+` 搜索条件、结果摘要、结果列表拆层
- 结果卡片在大屏进入更高信息密度模式

主策略：

- **重排**

## 5.4 书籍详情页

现状：

- 已有限宽
- 结构仍偏手机顺序式堆叠

建议：

- `600+` 封面、摘要、操作区、目录预览分栏
- 当前章节、缓存、换源模块不要都保持单列竖排

主策略：

- **重排**

## 5.5 阅读设置弹层

现状：

- 外层已有自适应
- 内层之前存在较多固定值

建议：

- 保留面板结构
- 用面板宽度计算缩放因子
- 对胶囊卡片、背景图卡片、色板、间距做等比调整
- 必要时把顶部快捷入口从固定 3 列改成 2/3/4 列切换

主策略：

- **局部缩放为主，局部重排为辅**

## 6. 统一实现建议

## 6.1 页面级模板

信息流页面优先复用：

- `LayoutBuilder`
- `Align(topCenter)`
- `ConstrainedBox(maxWidth: ...)`
- 根据 `constraints.maxWidth` 切布局

不是只做到：

- `ConstrainedBox(maxWidth: ...)`

而是做到：

- `ConstrainedBox(maxWidth: ...) + 内容结构变化`

## 6.2 控制面板模板

控制面板建议统一：

- 基准宽度：例如 `360`
- 面板宽度 / 基准宽度 = `scale`
- 缩放范围 clamp 在合理区间，例如 `0.94 ~ 1.18`

允许缩放的内容：

- 图标尺寸
- 控件高度
- 内边距
- 间距
- 圆角
- 胶囊卡片尺寸
- 色板点尺寸
- 预设背景卡片尺寸

谨慎缩放的内容：

- 正文字号
- 标题字号
- 长文案字号

原因：

- 文本语义稳定性优先于视觉同比例

## 7. 后续执行优先级

### 第一阶段

- 阅读设置弹层：完成等比缩放规则统一
- 书源页：启动大屏结构改造

### 第二阶段

- 书架页：大屏内容区重排
- 搜索页：结果区重排

### 第三阶段

- 详情页：大屏分栏
- 其他设置页：统一面板策略

## 8. 最终口径

当前项目后续统一按这个原则推进：

- **页面型信息区：优先重排**
- **控制型面板区：优先局部缩放**
- **全局只做容器限宽，不算自适应完成**

一句话总结：

**你的项目应该采用“约束驱动重排 + 小范围等比缩放”的常用组合方案。**
