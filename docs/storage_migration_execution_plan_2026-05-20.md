## 1. 目标

本计划用于指导项目完成存储治理改造，重点解决以下问题：

- 多次覆盖安装后卡顿
- 持久化边界不清
- 用户资产与缓存混放
- `SharedPreferences` 数据膨胀
- 清理逻辑误删用户资源
- 数据库升级链缺少系统验证

本轮不是继续增强“清理能力”，而是要完成一次存储职责重构。

## 2. 改造原则

整个改造过程统一遵循以下原则：

1. 可重建的才叫缓存
2. 用户资产不能进入缓存目录
3. 结构化且会增长的数据优先数据库
4. `SharedPreferences` 只保留轻量偏好和轻量状态
5. 敏感信息统一走安全存储
6. 任何改造都不能以牺牲老用户升级稳定性为代价

## 3. 本轮范围

纳入本轮治理范围：

- `SharedPreferences`
- `drift/sqlite`
- 托管文件目录
- 本地缓存目录
- `flutter_secure_storage`
- 启动阶段的存储维护和迁移逻辑

本轮优先关注的模块：

- 高级主题
- 封面图集
- 启动图集
- 本地图书
- 阅读缓存
- 书源状态
- 书架状态
- 同步配置

## 5. Phase 0：止血与冻结

### 5.1 目标

在正式迁移前，先停止继续引入新的存储混乱。

### 5.2 执行动作

1. 禁止新增大 JSON 继续写入 `SharedPreferences`
2. 禁止新增用户资产写入缓存目录
3. 禁止新增“清理全部本地数据”一类模糊能力
4. 下线或隐藏容易误导用户的“存储管理/清理”入口
5. 停止启动时自动执行高风险清理逻辑

### 5.3 当前建议状态

当前“存储管理”入口和启动期存储维护逻辑已移除，可视为本阶段已部分完成。

### 5.4 验收标准

- 新需求评审时，涉及本地存储必须说明落位
- 没有新增模糊清理逻辑
- 没有新增大对象继续堆进 `SharedPreferences`

## 6. Phase 1：存储盘点

### 6.1 目标

把当前项目中所有本地持久化点完整找出来，建立清单，避免后续迁移漏项。

### 6.2 盘点维度

每一项数据至少记录以下字段：

- 模块
- 数据名称
- 当前存储位置
- 当前 key / 表 / 目录
- 数据示例
- 体积级别
- 是否增长
- 是否可重建
- 是否属于用户资产
- 是否敏感
- 是否影响升级
- 建议目标位置
- 迁移优先级

### 6.3 重点盘点对象

1. `SharedPreferences` 中所有 `setString` / `setStringList` / `setBool` / `setInt` 的业务含义
2. 数据库所有表、字段、迁移分支
3. 托管资源目录和路径恢复逻辑
4. 缓存目录、预算、清理逻辑
5. `flutter_secure_storage` 的使用点

### 6.4 产物

建议生成文档：

- `storage_inventory_2026-05-xx.md`

### 6.5 验收标准

- 所有持久化入口均有清单记录
- 可以明确区分业务数据、用户资产、缓存、敏感数据
- 可以看出高风险迁移对象列表

## 7. Phase 2：规则定版

### 7.1 目标

把“什么存哪里”形成统一规则，避免边迁移边返工。

### 7.2 规则输出内容

1. `SharedPreferences` 使用红线
2. 数据库使用场景
3. 托管文件目录规范
4. 缓存目录规范
5. 敏感信息规范
6. 清理逻辑边界规范
7. 新功能存储接入 checklist

### 7.3 关键决策点

需团队明确以下问题：

1. 高级主题、封面图集、启动图集最终走数据库索引还是文件索引
2. 书源登录状态、书籍自定义状态是否结构化表化
3. 本地图书派生资源中哪些是资产，哪些是缓存
4. 缓存是否统一引入注册表机制

### 7.4 产物

- 定版后的存储规范文档
- 新功能存储接入 checklist

### 7.5 验收标准

- 团队对存储边界达成一致
- 高风险模块都有明确目标落位
- 后续开发可以按规则直接执行

## 8. Phase 3：高风险迁移

### 8.1 目标

优先解决最可能导致覆盖安装后卡顿和膨胀的问题。

### 8.2 优先级

优先迁移以下高风险项：

1. `SharedPreferences` 中的大 JSON 集合
2. 用户资产与缓存混放的数据
3. 与启动期强耦合的大体积反序列化对象
4. 修改频繁但粒度过粗的聚合式对象

### 8.3 第一批建议迁移对象

#### A. 高级主题

当前问题：

- 全量主题集合以 JSON 形式存储
- 体积会随主题数量和资源绑定持续增长
- 启动和页面加载需要整体反序列化

建议方向：

- 主题元数据走数据库或轻量索引
- 资源引用走托管文件相对路径
- 大对象不再整体放入 `SharedPreferences`

#### B. 封面图集

当前问题：

- 图集元数据以 JSON 聚合存储
- 路径恢复和资源目录绑定较重

建议方向：

- 图集索引结构化
- 图片文件留在托管目录
- 图集展示只读取索引和首图摘要

#### C. 启动图集

当前问题：

- 图集配置和启动快照耦合
- 图集规模增长后，配置读取成本会升高

建议方向：

- 图集索引结构化
- 启动快照与图集索引解耦
- 启动阶段只读取最小必要数据

#### D. 聚合式书源状态 / 书籍自定义状态

当前问题：

- 业务状态聚合后不利于增量更新和局部修复

建议方向：

- 拆分为结构化表或稳定索引对象
- 避免全量覆盖写入

### 8.4 实施顺序建议

1. 先建目标模型
2. 再补迁移逻辑
3. 再切换读取路径
4. 最后删除旧存储写入逻辑

### 8.5 迁移策略建议

每个迁移项统一使用以下策略：

1. 新老双读
2. 新写优先写新结构
3. 启动或首次访问时完成单向迁移
4. 迁移成功后记录版本标记
5. 观察稳定后移除旧结构读取

### 8.6 验收标准

- 高风险对象不再依赖 `SharedPreferences` 全量 JSON
- 启动阶段大对象读取明显减少
- 用户资源路径稳定，不受缓存清理影响
- 老用户升级后数据可用

## 9. Phase 4：缓存体系收敛

### 9.1 目标

统一缓存的定义、目录、预算、清理方式和生命周期。

### 9.2 需要治理的缓存类型

- 章节缓存
- 分页缓存
- 封面下载缓存
- 可重建临时解析产物
- 运行时临时文件

### 9.3 必须补齐的字段

每类缓存都应明确：

- 缓存名称
- 存储目录
- key 规则
- 来源
- 是否可重建
- 最大条目数
- 最大体积
- 过期策略
- 清理触发策略

### 9.4 改造要求

1. 用户资产目录与缓存目录彻底分离
2. 清理逻辑只能触碰缓存注册表中的目录
3. 不允许通过模糊路径匹配清理“历史残留”
4. 缓存预算要有统一配置出口
5. 启动期不再做高风险清理

### 9.5 验收标准

- 缓存定义清晰
- 清理边界单一明确
- 无法再误删用户资源
- 覆盖安装后不会因缓存清理导致资产缺失

## 10. Phase 5：升级链与回归

### 10.1 目标

确保老用户跨版本覆盖安装时，数据迁移稳定可靠。

### 10.2 必做项

1. 数据库升级链测试
2. 旧结构到新结构的迁移测试
3. 覆盖安装场景回归
4. 删除重装与覆盖安装行为差异验证
5. 资源路径恢复验证

### 10.3 覆盖安装回归矩阵建议

至少覆盖：

- 低版本直接升级到当前版本
- 中间版本升级到当前版本
- 多次连续覆盖安装
- 升级后首次启动
- 升级后长时间未打开再启动

### 10.4 重点验证数据

- 本地图书是否仍可打开
- 自定义封面是否仍存在
- 背景图、启动图、底栏图标、字体是否恢复正常
- 阅读记录、书签、书架状态是否完整
- 同步配置和 secret 是否正常

### 10.5 验收标准

- 升级链测试通过
- 老用户升级后关键数据无丢失
- 不再依赖“建议用户删除重装”解决问题

## 11. Phase 6：防回退治理

### 11.1 目标

防止改完之后，后续新需求又把存储边界写乱。

### 11.2 建议措施

1. 代码评审 checklist 增加“存储落位说明”
2. 新增功能必须说明是否是资产、业务数据、缓存、敏感数据
3. 对 `SharedPreferences` 新增大对象写入做审查
4. 引入简单的存储治理文档和目录约定
5. 必要时增加静态扫描脚本，检查可疑大 JSON 写入点

### 11.3 建议监控项

- 启动期关键持久化读取耗时
- `SharedPreferences` 关键 key 数量和体积
- 缓存目录总大小
- 数据库文件体积变化
- 迁移执行成功率

### 11.4 验收标准

- 新需求有统一落位标准
- 新增大对象写入可被发现
- 存储边界文档长期可维护

## 13. 风险与回滚策略

### 13.1 主要风险

1. 老用户数据迁移不完整
2. 新旧结构双读期间状态不一致
3. 路径恢复失败导致资源丢失
4. 启动期迁移过重导致首启变慢

### 13.2 缓解策略

1. 每个迁移项都使用双读单写过渡
2. 路径迁移必须保留旧路径兼容窗口
3. 迁移失败不能阻塞主流程
4. 迁移必须可重复执行且幂等
5. 关键迁移增加日志与统计

### 13.3 回滚原则

1. 先保读，再保写
2. 回滚时优先恢复旧读取链路
3. 不允许通过“直接删本地数据”作为回滚方案
4. 不允许通过再次引入模糊清理逻辑处理迁移事故
