# 漫画书源兼容计划（基于 `manhua.json`）

目标：在不破坏现有小说链路稳定性的前提下，分阶段支持 Legado 漫画书源（`bookSourceType=2`），最终实现“可导入、可检索、可看图、可缓存、可定位问题”。

参考规则文档：
- https://mgz0227.github.io/The-tutorial-of-Legado/Rule/source.html

## 1. 样本分析结论（`manhua.json`）

当前样本具备以下特征：
- `bookSourceType = 2`（漫画源）。
- `searchUrl`、`exploreUrl`、`header` 为 `<js> ... </js>`。
- `ruleSearch.bookList`、`ruleBookInfo.init`、`ruleToc.chapterList`、`ruleContent.content` 也依赖 `<js>`。
- 多处脚本通过 `Reload('https://qyyuapi.com/...')` 远程拉取 JS 再执行。
- `ruleContent.imageStyle = FULL`，正文是图片流，不是纯文本。

结论：该样本属于“JS 重依赖 + 图片正文”的漫画规则，当前项目无法直接兼容。

## 2. 当前能力缺口（对照现有代码）

- 数据模型层
  - `SourceDefinition` 尚无 `sourceType`、`contentMode` 等字段，导入后无法稳定区分“小说源/漫画源”。
- 规则执行层
  - 搜索/详情/目录/正文规则归一化阶段会跳过或丢弃 `js` 规则；`Reload(...)` 未实现。
- 搜索交互层
  - 搜索页还没有“搜索小说/搜索漫画”切换，用户无法按内容类型筛选书源执行搜索。
- 阅读内容层
  - `ChapterContentService` 目前只返回纯文本 `String`，没有图片章节载体。
- 阅读 UI 层
  - 阅读页目前是文本分页/滚动模式，没有漫画纵向图流模式。
- 缓存层
  - 章节缓存表当前只缓存文本，未覆盖图片 URL 列表、图片下载状态。
- 可观测性
  - 导入时缺少“能力不支持”诊断（例如 `js/reload` 未支持），用户只能看到网络或解析失败。

## 3. 兼容策略（稳定保守）

先做“可识别 + 可降级 + 不崩溃”，再做“JS-Free 漫画闭环”，最后评估“完整 JS/Reload”。

## 4. 建议实施顺序（避免返工）

1. 先完成 M0（能力识别 + 搜索类型切换 + 清晰报错）。
2. 再完成 M1（先把 JS-Free 漫画跑通，建立图片阅读基础设施）。
3. 最后推进 M2（JS/Reload），并对 `manhua.json` 做专项回归。

## 5. 风险与决策点

- 风险 1：`Reload(...)` 依赖第三方远程脚本服务，稳定性和可用性不可控。
- 风险 2：JS 执行如果放在主线程，容易导致 Android ANR。
- 风险 3：漫画图片资源体积大，若直接离线下载会放大存储压力。

需要明确的技术决策：
- 是否接受引入 JS 引擎依赖（体积、维护成本、平台一致性）。
- `Reload` 脚本缓存策略（TTL、失败回退、离线兜底）。
- 漫画缓存一期是否仅做“URL 清单缓存”（建议先这样，最稳）。
