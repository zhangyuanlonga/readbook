# 项目核心方针

更新时间：2026-06-02

本文是 Selune 后续开发的最高口径。它不解决某一个功能怎么写，而是定义“什么样的改动才让项目变得更好”。

## 1. 项目目标

Selune 的目标不是把移动端页面简单拉宽到 Web 和桌面端，而是形成一个可长期维护的多端阅读应用：

- Android / iOS 保持稳定，不因多端适配被反复扰动。
- Web / macOS / Windows / Linux 复用业务内核，但拥有符合各自平台习惯的外壳、交互和降级策略。
- 阅读、书架、搜索、详情、主题、账号、缓存、存储等核心业务形成清晰边界。
- 后续开发优先使用 Flutter 官方能力、成熟开源库和项目内稳定组件，减少重复手写代码。
- 每次改动都能被测试、构建、文档和回归清单解释。

## 2. 最高原则

- 业务内核复用，平台能力隔离。
- 页面负责展示和意图分发，不负责组装仓库、数据库、平台插件。
- 平台差异先进入 capability、adapter、bridge、conditional import，不进入页面散点判断。
- UI 先使用项目已有 token、adaptive 组件和 Flutter Material 体系，再考虑新组件。
- 稳定移动端只做必要兼容和等价抽取，不为桌面端重写成熟移动端体验。
- 新功能先设计业务边界，再写页面。
- 能用成熟库解决的通用问题，不手搓第二套。
- 能用自动化验证守住的规则，不只靠口头约定。

## 3. 当前工程判断

项目已经具备多端化基础：

- 标准 Flutter 平台目录已包含 Android、iOS、Web、macOS、Windows、Linux。
- 路由使用 GoRouter，状态和依赖注入使用 Riverpod。
- 本地数据库使用 Drift，原生和 Web 数据库已经通过条件导出隔离。
- 已有 `AppLayout`、`AppAdaptiveMetrics`、Adaptive 组件和桌面 shell。
- 已有架构、存储、UI、主题、路由等治理脚本。

当前需要治理的重点：

- 超大页面和超大 service 影响维护与测试。
- 页面层仍有不少 `kIsWeb`、`defaultTargetPlatform`、`Platform` 分支。
- 部分模型、JSON、copyWith、偏好存储仍然手写较多。
- UI token 已建立，但局部页面仍有硬编码颜色、圆角、尺寸和弹层形态。
- Web JS 可构建，Web WASM 需要独立专项治理。
- Windows / Linux 需要进入 CI 或对应平台机器验证。

## 4. 开发优先级

后续任务按这个顺序判断价值：

1. 不破坏移动端稳定性。
2. 打通 Android / iOS / Web / Desktop 真实业务链路。
3. 消除架构反向依赖和平台 import 风险。
4. 拆分复杂页面，降低单文件复杂度。
5. 用成熟库和生成工具减少手写样板。
6. 用统一 UI token 和 adaptive 组件提升一致性。
7. 建立自动化守卫，让同类问题不反复出现。

## 5. 不做什么

- 不把每个页面都做成“全平台万能 widget”。
- 不为了追求新技术一次性重写稳定移动端。
- 不为了升级依赖一次性 major upgrade 全部包。
- 不把平台能力失败留给用户点击后报错。
- 不在页面里直接读写数据库、文件系统、SharedPreferences 或平台通道。
- 不新增没有入口、没有验收、没有回归方式的临时文档。

## 6. 每次改动的基本交付

每次功能或治理改动至少说明：

- 影响的业务链路。
- 影响的平台。
- 是否修改共享层。
- 使用了哪些已有组件、token、provider、service 或成熟库。
- 不支持平台如何降级。
- 跑过哪些测试、构建或 guard。
- 文档是否需要同步更新。
