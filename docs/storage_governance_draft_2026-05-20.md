# 存储治理草案

更新时间：2026-05-20

状态：草案，供团队讨论，不作为最终定版规范

## 1. 背景

当前项目经过多轮迭代后，用户存在多次覆盖安装的典型场景。现象上表现为：

- 老用户覆盖安装次数较多后，应用出现明显卡顿
- 删除重装后，应用恢复流畅
- 之前尝试通过“缓存清理”缓解，但收益不明显
- 历史清理逻辑还带来了误伤风险，出现“用户几天没打开，之前导入的资源被清空”的问题

这说明当前问题大概率不是“单一缓存过大”，而是以下问题叠加：

- 本地持久化边界不清，业务数据、用户资产、缓存数据混放
- `SharedPreferences` 承担了过多结构化数据存储职责
- 本地数据库、托管文件、缓存目录之间缺少明确职责划分
- 启动期或用户侧清理逻辑无法稳定区分“可删缓存”和“不可删用户资产”
- 覆盖安装链路下的历史残留没有系统治理

因此，本轮目标不是继续补“清理按钮”，而是先完成存储治理边界重构。

## 2. 本轮目标

本轮建议明确以下目标：

1. 停止继续扩大存储边界混乱
2. 明确每类数据应该存在哪里
3. 把“用户资产”和“缓存”彻底隔离
4. 为后续迁移、压缩、清理、升级测试建立统一标准
5. 为覆盖安装场景建立可验证的稳定升级路径

## 3. 核心原则

建议后续统一遵循以下原则：

### 3.1 可重建的，才叫缓存

满足以下条件的数据，才能定义为缓存：

- 删除后不会造成用户资产丢失
- 删除后功能仍可正常使用
- 删除后只是需要重新计算、重新下载、重新解析
- 可以接受命中率下降，但不能影响数据完整性

反过来，只要删除后用户会感知“我的内容没了”，就不能定义为缓存。

### 3.2 用户资产不能进入缓存目录

用户主动导入、创建、编辑、绑定的资源，必须视为用户资产，例如：

- 本地图书源文件
- 自定义封面
- 字体
- 背景图
- 启动图
- 底栏图标素材
- 主题关联图片

这类数据必须与缓存目录彻底隔离，且任何缓存清理逻辑都不能触碰。

### 3.3 结构化且会增长的数据，优先数据库

满足以下条件的数据，优先进入本地数据库，而不是 `SharedPreferences`：

- 需要增删改查
- 会持续增长
- 需要筛选、排序、分页、聚合
- 有关联关系
- 后续可能要做升级迁移

### 3.4 SharedPreferences 只存轻量偏好

`SharedPreferences` 的职责应该被限制为：

- 小体积
- 低复杂度
- 用户偏好
- 启动期快速读取的轻量状态

不建议继续承载大 JSON、可增长列表、资源清单、复杂业务快照。

### 3.5 敏感数据单独走安全存储

密码、token、secret、密钥类数据，不允许混入普通偏好或数据库明文存储，应统一走 `flutter_secure_storage`。

## 4. 存储分层建议

建议项目后续统一拆成以下 5 层：

### 4.1 SharedPreferences

适合存储：

- 开关项
- 主题模式
- 导航样式
- 轻量阅读设置
- 最后选中页签
- 启动页开关
- 一次性引导状态
- 任务 gate 标记

不适合存储：

- 大 JSON
- 用户资源列表
- 图集全集
- 高级主题全集
- 复杂书架快照
- 可持续增长的记录

建议约束：

- 单 key 应尽量控制在几 KB 以内
- 总体只用于“偏好设置”和“轻量状态”
- 新功能接入时，默认先问“为什么不是数据库”

### 4.2 本地数据库

适合存储：

- 业务主数据
- 本地导入书籍索引
- 章节索引与章节内容
- 阅读记录
- 书签
- 书源信息
- 书籍元数据覆盖信息
- 搜索命中记录
- 同步配置元数据

不适合存储：

- 图片二进制本体
- 字体文件本体
- 大体积媒体资源
- 纯临时运行时缓存文件

建议约束：

- 只要数据“不能丢、不可随便清、未来要迁移”，优先数据库
- 所有数据库升级都要可回放、可测试

### 4.3 托管文件目录

适合存储：

- 用户导入的本地图书文件
- 自定义封面文件
- 阅读背景图
- 启动图
- 底栏图标资源
- 字体文件
- 主题绑定素材

建议目录特性：

- 与缓存目录彻底分离
- 路径稳定
- 支持相对路径持久化
- 支持启动时路径恢复
- 支持覆盖安装后继续可用

### 4.4 本地缓存目录

适合存储：

- 章节缓存
- 分页缓存
- 封面下载缓存
- 可重建的解析结果
- 运行时临时文件

必须满足：

- 可以删
- 删了不会丢用户资产
- 删了只影响性能，不影响正确性
- 有预算上限
- 有过期策略

### 4.5 安全存储

适合存储：

- token
- 密码
- WebDAV secret
- 其他敏感凭证

不适合存储：

- 普通偏好
- 业务主数据
- 大 JSON

## 5. 结合当前项目的建议落位

以下为基于当前仓库现状的建议落位，不是最终定稿，但可作为迁移方向。

### 5.1 应继续放在本地数据库的数据

当前适合保留或继续增强为数据库存储的内容：

- `local_books`
- `local_chapters`
- `reading_records`
- `reading_record_days`
- `reading_record_sessions`
- `bookmarks`
- `script_sources`
- `book_metadata_overrides`
- `search_source_hits`
- `sync_profiles`

建议后续重点评估是否表化的内容：

- 书源登录状态聚合数据
- 书籍自定义状态聚合数据
- 复杂书架视图快照
- 主题/图集索引元数据

### 5.2 应归为托管文件的数据

建议视为用户资产，放在托管文件目录：

- 本地图书源文件
- 本地图书派生资源
- 自定义封面文件
- 背景图
- 启动图
- 底栏图标文件
- 字体文件
- 主题绑定的图片资产

### 5.3 应归为缓存的数据

建议继续视为缓存，但要统一治理：

- 章节缓存
- 分页布局缓存
- 封面磁盘缓存
- 可重建的运行时临时缓存

缓存必须具备统一协议：

- 明确目录
- 明确 key 规则
- 明确大小预算
- 明确清理策略
- 明确过期策略
- 明确“删了是否可完全恢复”

### 5.4 应从 SharedPreferences 中逐步迁出的内容

当前高风险项主要是“结构化 JSON 集合”：

- 高级主题全集
- 封面图集全集
- 启动图集全集
- 部分复杂阅读快照
- 部分复杂书架聚合配置
- 部分来源登录状态或业务状态聚合对象

这类数据继续放在 `SharedPreferences`，风险主要有：

- 覆盖安装后累积膨胀
- 冷启动反序列化成本高
- 修改粒度过粗，写放大明显
- 难以做增量迁移
- 容易和用户资源路径强耦合

## 6. 当前已识别的重点风险

### 6.1 SharedPreferences 数据膨胀

当前仓库中可见多处将结构化 JSON 直接写入 `SharedPreferences`。这类数据如果持续增长，会带来：

- 启动读取成本上升
- JSON 解码成本上升
- 覆盖安装后膨胀难以治理
- 数据边界继续模糊

### 6.2 用户资产与缓存边界不清

历史上“存储管理/缓存清理”逻辑承担过过多责任，容易导致：

- 清理逻辑误删非缓存资源
- 历史残留清理与当前资产目录冲突
- 用户长时间未打开后再次启动出现资源缺失

### 6.3 数据库升级链缺少系统验证

当前数据库版本已较高，升级分支较多。若缺少完整升级链测试，覆盖安装场景下可能出现：

- 部分表升级不完整
- 历史字段未兼容
- 某些版本跨级升级失败
- 低频用户升级后才暴露问题

### 6.4 热修复式兼容残留

当前仓库仍存在一些平台侧补丁和兼容脚本。它们不是直接问题根因，但说明历史上已经积累了不少特殊处理。后续如果不梳理清楚，容易继续放大覆盖安装复杂度。

## 7. 建议的治理计划

建议按 4 个阶段推进。

### 阶段 1：存储清单盘点

目标：

- 把所有本地持久化点找全
- 建立统一清单

建议产物字段：

- 模块
- 数据名称
- 当前存储位置
- 当前 key/表/目录
- 数据示例
- 体积级别
- 是否会增长
- 是否可重建
- 是否属于用户资产
- 是否影响升级
- 建议目标位置
- 迁移优先级

### 阶段 2：边界定规

目标：

- 在团队内先定标准，再开始迁移

建议产物：

- 存储分类规范
- 缓存定义规范
- 用户资产目录规范
- SharedPreferences 使用红线
- 新功能接入 checklist

### 阶段 3：高风险项迁移

建议优先级：

1. 迁出 `SharedPreferences` 中的大 JSON 集合
2. 拆分用户资产目录与缓存目录
3. 收敛缓存清理入口，只允许清理真正可重建的缓存
4. 为关键业务数据补数据库化或索引化

建议首批整改对象：

- `advanced_theme_service`
- `cover_gallery_service`
- `launch_image_gallery_service`
- 聚合式登录状态和书籍状态对象

### 阶段 4：验证与防回退

目标：

- 防止这次整理后，后续新功能又把边界写乱

建议补充：

- 覆盖安装回归清单
- 数据库升级链测试
- 启动期关键存储体积日志
- 关键 `SharedPreferences` key 体积监控
- 缓存预算检查
- 代码评审 checklist

## 8. 建议的判断标准

后续遇到一个新数据项时，可以按以下顺序判断：

1. 这是用户资产吗
2. 删除后用户会感知吗
3. 这是敏感信息吗
4. 这类数据会增长吗
5. 需要查询、排序、关联吗
6. 只是为了性能而存在吗

建议映射如下：

- 用户资产：托管文件
- 敏感小数据：安全存储
- 结构化业务数据：数据库
- 轻量偏好：SharedPreferences
- 可重建临时数据：缓存

## 9. 本轮建议结论

结合当前问题现象，本轮建议结论如下：

1. 不再依赖“存储管理”或“缓存清理”作为核心治理手段
2. 优先做存储边界治理，而不是继续做更强的清理能力
3. 用户资产与缓存必须彻底隔离
4. `SharedPreferences` 需要瘦身，只保留轻量偏好和轻量状态
5. 复杂结构化数据应逐步迁移到数据库或文件索引
6. 数据库升级链测试要纳入必做项

## 10. 待团队确认的问题

以下问题建议在讨论时重点确认：

1. 高级主题、封面图集、启动图集，最终是走数据库索引还是文件索引
2. 书源登录状态和书籍自定义状态，是否要从聚合 JSON 改成结构化表
3. 本地图书派生资源的生命周期如何定义，哪些属于资产，哪些属于可重建产物
4. 覆盖安装兼容测试需要覆盖哪些最低版本起点
5. 是否需要引入统一的“存储注册表”或“缓存注册表”机制，避免未来再次散落
