# 搜索模式与资源治理设计方案

创建日期：2026-06-02

状态：设计草案

适用范围：移动端普通搜索、深度搜索、后端搜索调度、多客户端并发、书源可见性、后台运维治理。

核心结论：默认搜索不能把 2000+ 书源全部扫一遍。普通搜索要快、稳、省资源；深度搜索要用户明确触发、可取消、可复用、可限流、可观测。

简化落地口径：第一版不做复杂权限树和深度嵌套规则，只做“搜索池 + 现有书源分组可见性”。普通用户只看到允许普通用户看的书源分组；敏感、18 禁、测试、低质量源可以由运维挪入特定书源分组，普通用户列表和搜索默认都排除。

第一版只保留三个关键判断：

- [ ] 这个源是否启用：`enabled`。
- [ ] 这个源属于哪个搜索池：`quick / deep / manualOnly / disabled`。
- [ ] 这个源所在现有书源分组是否对当前用户可见。

## 1. 当前问题

当前移动端全源搜索默认走 SSE：

```text
Flutter -> GET /api/v1/books/search/stream
```

现状特征：

- 普通搜索和“尽量搜全”的语义混在一起。
- 后端默认先取候选源批次，默认 `search_default_batch_size = 300`。
- SSE 默认生命周期 `search_stream_max_lifetime_secs = 30`。
- 多数情况下 30 秒内只能处理两百多个源，返回时用户容易误以为“已经全源搜完”。
- 如果未来把默认搜索改成每次都扫 2000+ 源，会造成用户空等、服务器空耗、上游书源压力和反爬风险。
- 移动端目前可以看到大量书源，后续后台运维需要控制“哪些源参与默认搜索、哪些人能看到哪些源、哪些源只能手动或深度搜索使用”。

## 2. 设计目标

- [ ] 普通搜索首屏快，优先返回高质量命中。
- [ ] 深度搜索可以覆盖更多源，但必须用户明确触发。
- [ ] 搜索结果必须明确标记是否完整，不能让用户误解。
- [ ] 多客户端相同搜索应尽量合并、复用缓存，减少重复上游请求。
- [ ] 深度搜索必须可取消、可限流、可排队、可观测。
- [ ] 书源可见性和可搜索范围必须可由后台运维控制。
- [ ] 普通用户默认不应该看到和扫到所有内部源、低质量源、冷却源、测试源。
- [ ] 所有搜索设计必须优先考虑性能、服务器成本、上游书源压力和无意义请求消耗。
- [ ] 第一版方案必须简单直接，不做过度设计，不引入复杂嵌套权限模型。

## 2.1 性能与资源红线

- [ ] 默认搜索不得全量轮询 2000+ 书源。
- [ ] 用户未明确触发深度搜索时，不得自动扩大搜索范围。
- [ ] 用户输入变化后，旧关键词搜索必须尽快取消。
- [ ] 客户端断开 SSE 后，后端必须停止剩余上游搜索任务。
- [ ] 深度搜索必须有时间上限、并发上限，并且可以取消。
- [ ] 同一用户同一关键词短时间重复搜索，必须优先复用缓存或未过期任务。
- [ ] 同一关键词多用户同时搜索，必须优先利用 inflight 合并或热缓存。
- [ ] 冷却中、长期失败、反爬风险高的源不得进入普通搜索池。
- [ ] 服务器繁忙时，必须优先保障普通搜索，降低或拒绝深度搜索。
- [ ] 搜索日志必须能回答“本次处理了多少源、浪费了多少源请求、为什么停止”。

## 3. 搜索模式

### 3.1 普通搜索

定位：默认入口，用户输入关键词后立即触发。

推荐策略：

- [ ] 默认只搜索“快速池”书源。
- [ ] 默认候选源控制在 200 到 300 个。
- [ ] 默认总耗时控制在 20 到 30 秒。
- [ ] 默认聚合相同书名作者，避免结果列表被重复源刷屏。
- [ ] 返回 `processedSourceCount`、`sourceCount`、`unprocessedSourceCount`。
- [ ] 如果未搜索完，移动端显示“已搜索 X/Y 个源，可继续深搜”。

普通搜索建议后端参数：

```text
searchMode=quick
sourcePool=quick
maxSources=300
deadlineSecs=30
concurrency=12
perHostConcurrency=2
```

普通搜索用户体验：

- [ ] 搜索时实时展示进度。
- [ ] 有结果就渐进渲染。
- [ ] 结束时如果未覆盖全部源，显示深度搜索入口。
- [ ] 用户继续输入新关键词时取消旧搜索。
- [ ] 普通搜索不承诺“全网搜完”。

### 3.2 深度搜索

定位：用户找不到书时主动触发，允许更久、更广、更明确地消耗资源。

触发方式分两种：

- [ ] 快速池跑完后仍未找到满意结果，移动端展示“继续深度搜索”。
- [ ] 用户在右上角更多菜单中主动选择“使用深度搜索”。

两种触发的语义不同：

- [ ] “继续深度搜索”承接当前普通搜索进度，优先跳过 quick pool 已处理源，继续搜索 deep pool。
- [ ] “使用深度搜索”表示用户一开始就选择更广范围，可以直接使用 deep 策略，但仍必须受并发、deadline 和服务器负载限制。
- [ ] 两种触发都必须展示更长耗时提示，并支持取消。
- [ ] 两种触发都不能绕过用户可见性和书源权限。

推荐策略：

- [ ] 必须由用户点击“继续深搜”或“搜索更多书源”触发。
- [ ] 不在用户输入过程中自动触发。
- [ ] 支持取消。
- [ ] 支持后台继续跑一小段，但必须有生命周期上限。
- [ ] 优先复用普通搜索已处理源，继续处理剩余源。
- [ ] 支持按批次推进，例如每批 300 个源。
- [ ] 支持阶段性结果缓存和进度恢复。

深度搜索建议后端参数：

```text
searchMode=deep
sourcePool=deep
target=completeVisibleDeepPool
batchSize=300
concurrency=8-12
perHostConcurrency=1-2
```

深度搜索的语义是“尽量搜完当前用户可见的 deep 范围”，不是“比普通搜索多跑一会儿”。第一版不设置固定总时长作为结束条件，结束条件只包括：源池搜索完成、用户取消、客户端断开、服务器繁忙保护。单个书源仍然保留 timeout，避免坏源拖死整次深搜。

深度搜索用户体验：

- [ ] 普通搜索结束后显示“继续深搜”。
- [ ] 搜索页右上角更多菜单提供“使用深度搜索”。
- [ ] 用户从更多菜单开启深搜时，搜索框附近显示“深度搜索中”状态。
- [ ] 深搜期间显示“已搜索 X/Y 个源，找到 N 个结果”。
- [ ] 用户可以停止深搜。
- [ ] 深搜结果追加到当前列表，保持去重和排序。
- [ ] 深搜结束后明确显示“已完成”或“因超时停止，可稍后继续”。

### 3.3 搜索完整性标记

后端响应和 SSE `end` 事件需要补充：

```json
{
  "partial": true,
  "stopReason": "deadline",
  "processedSourceCount": 236,
  "sourceCount": 2180,
  "unprocessedSourceCount": 1944,
  "canContinue": true,
  "nextCursor": "..."
}
```

建议 stopReason：

- [ ] `completed`：全部完成。
- [ ] `deadline`：达到本次搜索时间上限。
- [ ] `clientClosed`：客户端取消或断开。
- [ ] `serverBusy`：服务器负载过高。
- [ ] `sourcePoolExhausted`：当前源池已搜索完成。

## 4. 后端资源治理

### 4.0 简单执行顺序

搜索调度默认按最省请求的顺序执行：

```text
热缓存 -> inflight 复用 -> quick pool -> deep pool 批次 -> 手动源
```

任何需要扩大范围的行为，都必须满足：

- [ ] 用户明确触发。
- [ ] 服务器负载允许。
- [ ] 源池状态允许。
- [ ] 可以被取消。
- [ ] 可以被观测。

### 4.1 请求合并与缓存

当前已有能力：

- [x] 短 TTL 搜索缓存。
- [x] inflight 搜索合并窗口。
- [x] 每 user 活跃 SSE 搜索数限制。
- [x] 每 user + source 并发限制。

建议增强：

- [ ] 搜索缓存区分 `quick` 和 `deep`。
- [ ] 相同关键词、内容类型、源池、搜索模式的请求优先复用结果。
- [ ] 普通搜索缓存 TTL 可保持 10 到 30 秒。
- [ ] 深度搜索缓存 TTL 可提高到 5 到 15 分钟。
- [ ] 深度搜索中间结果按批次缓存，避免用户重复点击时从头扫。

### 4.2 深度搜索执行方式

第一版不新增搜索任务表，继续复用 SSE。

- [ ] 普通搜索走 `searchMode=quick`。
- [ ] 深度搜索走 `searchMode=deep`。
- [ ] 深度搜索必须用户明确触发。
- [ ] 深度搜索必须可取消。
- [ ] 深度搜索目标是完成当前用户可见的 deep 源池。
- [ ] 深度搜索不设置固定总时长作为默认停止条件。
- [ ] 单个书源必须有 timeout，避免坏源拖死深搜。
- [ ] 客户端断开后，后端停止未开始的源请求。

### 4.3 简单限流

普通搜索：

- [ ] 每用户同时普通搜索最多 1 到 2 个。
- [ ] 用户输入新关键词时取消旧普通搜索。

深度搜索：

- [ ] 每用户同时深度搜索最多 1 个。
- [ ] 服务器繁忙时降低深搜并发或拒绝新深搜。

系统级保护：

- [ ] 全局深度搜索并发上限。
- [ ] 单 host 并发上限。
- [ ] 单 source 冷却与失败降级。
- [ ] 服务器负载高时只允许普通搜索。
- [ ] 当 CPU、内存、连接数、上游失败率任一指标超过阈值时，自动降低深搜并发。
- [ ] 当上游失败率持续升高时，自动把相关源移出 quick pool 或进入冷却。

### 4.4 取消与浪费控制

- [ ] Flutter 端关键词变化时取消旧 SSE。
- [ ] 后端检测 SSE 断开后立即 abort 未完成任务。
- [ ] 深度搜索取消后不继续发起未开始的源请求。
- [ ] 同一用户同一关键词重复深搜，优先复用短期缓存。
- [ ] 同一关键词高频请求，优先返回缓存并提示结果更新时间。
- [ ] 移动端切后台或离开搜索页时，普通搜索默认取消。
- [ ] 深度搜索离开页面时弹出选择：继续后台跑或停止。
- [ ] 后端任务必须记录 stopReason，避免无声空跑。
- [ ] 后端任务必须设置硬 deadline，避免异常情况下无限占用资源。

### 4.5 服务器负载保护

建议后端维护运行时保护阈值：

- [ ] 活跃搜索任务数。
- [ ] 活跃深度搜索任务数。
- [ ] 当前上游请求数。
- [ ] 单 host 活跃请求数。
- [ ] 最近 1 分钟搜索失败率。
- [ ] 最近 1 分钟平均源耗时。
- [ ] SSE 客户端断开率。

触发保护时：

- [ ] 新普通搜索继续允许，但降低并发或只扫高质量 quick pool。
- [ ] 新深度搜索返回 `serverBusy`。
- [ ] 运行中的深度搜索降低并发或暂停下一批。
- [ ] 高失败源进入临时冷却。

## 5. 书源池设计

### 5.1 源池分层

建议每个书源有搜索池属性：

- [ ] `quick`：默认普通搜索池，高质量、稳定、速度快。
- [ ] `deep`：深度搜索池，可参与深搜，但不进入默认普通搜索。
- [ ] `manualOnly`：用户手动选源时才搜索。
- [ ] `disabled`：不参与搜索。
- [ ] `internal`：内部测试或运维可见。

第一版推荐实际只落四类：

- [ ] `quick`：普通搜索默认扫。
- [ ] `deep`：深度搜索才扫。
- [ ] `manualOnly`：用户手动指定才扫。
- [ ] `disabled`：不扫。

`internal` 可以先用分组可见性表达，例如把源放入“内部测试”分组，普通用户不可见。

普通搜索只扫：

```text
enabled=true
所在书源分组对当前用户可见
searchPool=quick
health 不在冷却
contentType 匹配
```

深度搜索可扫：

```text
enabled=true
所在书源分组对当前用户可见
searchPool in (quick, deep)
contentType 匹配
按健康状态排序，失败源靠后或跳过
```

### 5.2 源质量分层

建议后台维护以下指标：

- [ ] 搜索成功率。
- [ ] 详情成功率。
- [ ] 目录成功率。
- [ ] 正文成功率。
- [ ] 平均响应耗时。
- [ ] 近期失败次数。
- [ ] 冷却状态。
- [ ] 反爬或限流标记。
- [ ] 内容类型。
- [ ] 是否推荐进入普通搜索池。

质量分可以影响：

- [ ] 普通搜索排序。
- [ ] 深度搜索批次顺序。
- [ ] 是否进入 quick pool。
- [ ] 是否被自动降级到 deep 或 manualOnly。

## 6. 书源可见性与后台运维

### 6.1 用户可见性

第一版建议复用现有书源分组做可见性，不新建一套复杂分组体系，也不做复杂到人的权限表。

核心逻辑：

- [ ] 书源继续使用现有 `bookSourceGroup` / `group_name`。
- [ ] 后台只维护这些现有书源分组是否对普通用户可见。
- [ ] 普通用户只能看到“普通可见分组”里的启用书源。
- [ ] 普通搜索和深度搜索都必须先过滤不可见书源分组。
- [ ] 管理员和运维可以看到全部现有书源分组和全部书源。

建议第一版分组类型：

- [ ] 普通可见分组：普通用户可见，可参与普通搜索或深度搜索。
- [ ] 受限分组：普通用户不可见，例如 18 禁、敏感、风险源。
- [ ] 测试分组：普通用户不可见，仅管理员和运维可见。
- [ ] 维护分组：普通用户不可见，用于暂时下线、待验证、质量差的源。

普通用户默认看到：

- [ ] 启用状态为 `enabled=true` 的源。
- [ ] 所在现有书源分组对普通用户可见。
- [ ] 不显示受限、测试、维护分组里的源。

管理员看到：

- [ ] 全部源。
- [ ] 源状态。
- [ ] 健康报告。
- [ ] 搜索池配置。
- [ ] 分组可见性配置。
- [ ] 冷却与失败原因。

后续如果需要更细，再补“单书源可见性覆盖”；第一版先不做复杂到人规则。

### 6.2 运维维护能力

后台建议支持：

- [ ] 批量设置源池：quick、deep、manualOnly、disabled。
- [ ] 批量移动书源到指定分组。
- [ ] 设置分组是否对普通用户可见。
- [ ] 按健康状态筛选源。
- [ ] 按失败阶段筛选源：search、detail、toc、content。
- [ ] 按响应耗时筛选源。
- [ ] 按内容类型筛选源。
- [ ] 一键将失败源移出 quick pool。
- [ ] 一键将高质量源加入 quick pool。
- [ ] 搜索链路压测和抽样验证。

## 7. 移动端交互设计

普通搜索页面：

- [ ] 默认只触发普通搜索。
- [ ] 搜索中展示实时进度。
- [ ] 结果区优先展示已命中的结果。
- [ ] 普通搜索结束且 `partial=true` 时，展示“继续深搜”按钮。
- [ ] 右上角更多菜单提供“使用深度搜索”，作为主动深搜入口。
- [ ] 展示文案：`已搜索 X/Y 个源，找到 N 个结果`。

深度搜索入口：

- [ ] 从普通搜索结果页触发。
- [ ] 从右上角更多菜单主动触发。
- [ ] 从普通搜索结果页触发时，优先继续剩余源。
- [ ] 从更多菜单主动触发时，使用深度搜索策略重新组织源池和预算。
- [ ] 点击后说明会花更长时间。
- [ ] 支持取消。
- [ ] 支持结果追加。
- [ ] 支持深搜完成提示。

源管理页面：

- [ ] 普通用户默认不展示所有内部源。
- [ ] 可以展示“可用源数量”和“当前搜索范围”。
- [ ] 高级用户或管理员可以进入完整源管理。

## 9. 推荐落地顺序

第一优先：

- [ ] 先补 `partial/stopReason/canContinue`，让当前搜索结果不再误导用户。
- [ ] 移动端展示“已搜索 X/Y，可继续深搜”。

第二优先：

- [ ] 增加 `searchMode=quick/deep`。
- [ ] 普通搜索保持快，深度搜索明确用户触发。

第三优先：

- [ ] 深度搜索沿用 SSE，支持取消和 hard deadline。
- [ ] 引入源池和现有书源分组可见性，支撑后台运维。

第四优先：

- [ ] 后台管理 quick/deep/manualOnly/disabled 源。
- [ ] 后台基于现有书源分组管理普通可见、受限、测试、维护状态。
- [ ] 基于健康指标自动推荐源池调整。

## 10. 暂不建议

- [ ] 不建议把普通搜索默认改成 2000+ 全源扫描。
- [ ] 不建议单纯把 SSE 生命周期从 30 秒拉到几分钟。
- [ ] 不建议把所有源都直接暴露给普通用户。
- [ ] 不建议深度搜索无取消、无 deadline、无缓存复用。
