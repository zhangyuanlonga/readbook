# 功能级 UI / 业务清扫阶段计划

更新时间：2026-05-06  
用途：针对全项目“按开发约束拆分后”可能引入的复杂化、性能拖沓、体验下降问题，提供一个更完整、可执行、按阶段推进的清扫计划。  
适用范围：`announcement`、`auth`、`book`、`bookshelf`、`discover`、`error`、`home`、`mine`、`reader`、`search`、`source`、`sync`

---

## 1. 计划目标

本计划不只看单点性能，而是同时覆盖：

- UI 层：卡顿、掉帧、空白、重建面过大、交互迟滞
- 业务层：链路过长、编排过重、状态补齐时机差、复杂度失控
- 架构层：页面承担过多逻辑、依赖边界模糊、Provider 订阅范围过宽

最终目标：

- 高频功能先恢复“顺滑、稳定、首屏快”
- 中频功能避免“越拆越复杂、越改越重”
- 低频功能保证“不恶化、易维护”

---

## 2. 执行原则

- 每阶段必须同时看 UI 与业务，不只看单点代码警告
- 每阶段都需要有“用户体感目标”和“工程验收目标”
- 高频路径优先于低频管理页
- 公共基础设施问题优先于 feature 局部修补
- 能批量预计算的，不做 item 级重复计算
- 能后置到首屏后的，不阻塞首屏
- 每完成一个阶段，同步更新文档勾选状态

---

## 3. 风险分层

### 3.1 高频核心功能

- `bookshelf`
- `book`
- `reader`
- `discover`
- `search`
- `home`

特点：

- 用户天天用
- 一旦拖慢，体感非常明显
- 首屏、滚动、点击跳转必须优先保障

### 3.2 中频复杂功能

- `mine`
- `source`
- `sync`

特点：

- 功能密度高
- 页面和业务都容易膨胀
- 主要风险是“过度复杂化 + 可维护性下降”

### 3.3 低频轻功能

- `announcement`
- `auth`
- `error`

特点：

- 结构相对简单
- 更适合做稳定性和边界检查

## 5. 功能维度检查模板

后续每个 feature 清扫时，建议统一按下面四项记录：

### UI

- [ ] 是否有 build 期同步 IO
- [ ] 是否有 item 级异步
- [ ] 是否有根部过宽订阅
- [ ] 是否有滚动 / 首屏 / 动画体感问题

### 业务

- [ ] 是否有首屏阻塞链路
- [ ] 是否有页面承担过多编排
- [ ] 是否有状态补齐时机不合理

### 复杂度

- [ ] 页面文件是否过大
- [ ] application 是否承接不够
- [ ] Provider 粒度是否合理

### 验收

- [ ] `flutter analyze`
- [ ] 对应测试或 smoke
- [ ] 真机 / 录屏体感复核
