# 阅读记录重构方案

更新时间：2026-04-04  
用途：将当前阅读记录从“多张聚合表 + 页面自行拼装”的兼容实现，收口为“统一阅读事件流 + 明确投影模型”的可执行改造方案。

## 1. 当前判断

当前阅读记录的问题不是“页面不好看”，而是三层问题叠在一起：

- 数据主键错位
- 聚合模型分叉
- 页面职责越界

现在的实现表面上支持：

- 最近阅读
- 按天汇总
- 时间线
- 热力图
- 搜索
- 删除撤销
- 阅读记录合并

但这些能力并不是建立在同一套清晰模型上，而是：

1. 先写入 session
2. 同步写 latest / day 两层聚合
3. 页面再把三层数据重新组合
4. 页面额外补一层“临时合并”和“临时统计”

这导致页面看起来功能很多，实际上语义并不稳定。

## 2. 当前核心问题

### 2.1 记录主键仍然绑定 `bookId`

当前阅读记录的核心主键仍然是 `bookId`，而不是“作品身份”。

这会直接导致：

- 同一本书换源后天然分裂成多条记录
- 搜索页、阅读页、换源页已经在强调“源可切换”
- 阅读记录却仍然把“源内 bookId”当成最终身份

后果：

- 记录碎片化
- 热力图碎片化
- 摘要卡碎片化
- 必须依赖“按标题猜测合并”来补救

### 2.2 三层数据不是投影关系，而是并列维护

当前同时维护：

- `reading_records`
- `reading_record_days`
- `reading_record_sessions`

问题不在于“三张表”本身，而在于：

- 它们不是从同一个只读事实流派生出来的稳定投影
- 而是在写入阶段同步维护
- 删除、恢复、合并后再重建

这意味着：

- 聚合正确性依赖写入路径和重建逻辑全部正确
- 页面层还要再额外做二次合并
- 任何一个动作都可能让三层数据短暂不一致

### 2.3 时间线展示模型和删除模型不一致

当前时间线会把相邻 session 临时合并成一段更长的“阅读会话”，但删除时删的仍然只是单条底层 session。

这会导致：

- 用户看到的是 A
- 实际删除的是 B

这是语义级 bug，不是体验小问题。

### 2.4 热力图指标命名和实际统计不一致

当前热力图提供：

- 按时长
- 按次数

但“按次数”实际统计的是：

- 当天有多少条 `ReadingRecordDay`
- 也就是“当天有多少本书留下了日聚合”

它不是：

- 会话次数
- 阅读动作次数
- 打开次数

也不是用户直觉里的“阅读次数”。

这是典型的指标语义错位。

### 2.5 页面已经承担了服务层职责

当前阅读记录页自己做了太多事：

- 三层流拼接
- 热力图统计
- 摘要卡汇总
- 时间线会话合并
- 日期过滤
- 空态策略

结果：

- 页面不是展示层，而是 orchestration 层
- 任何指标调整都要改 UI
- 很难做测试
- 很难抽出自己的产品逻辑

## 3. 重构目标

本轮重构目标不是“把页面做漂亮”，而是先把记录模型拉直。

明确目标：

- 阅读记录以“阅读事件 / 阅读会话”为唯一事实来源
- “最近阅读 / 按天汇总 / 热力图 / 时间线”都只是投影
- 作品身份不再直接等于某个书源内的 `bookId`
- 页面不再自行拼装统计逻辑
- 指标命名必须和实际含义一致

非目标：

- 不优先做视觉重设计
- 不优先做复杂社交型数据分析
- 不在第一阶段追求跨端同步

## 4. 新模型建议

### 4.1 引入作品级身份 `workKey`

建议新增作品级阅读身份，而不是继续把 `bookId` 当作阅读记录主键。

建议语义：

- `workKey`：阅读记录主身份
- `sourceId + bookId`：来源身份

`workKey` 的来源建议：

1. 书架已有绑定时，直接复用书架项身份
2. 换源成功时，把多个来源映射到同一个 `workKey`
3. 无法确认时，允许先挂临时 `workKey`
4. 明确人工确认合并后，再收敛到稳定 `workKey`

这一步是整个改造的核心。

### 4.2 用 session/event 做事实表

建议把 session 作为唯一事实层。

最小字段：

- `sessionId`
- `workKey`
- `bookId`
- `sourceId`
- `detailUrl`
- `bookTitle`
- `bookAuthor`
- `coverUrl`
- `chapterId`
- `chapterTitle`
- `chapterIndex`
- `chapterUrl`
- `startAt`
- `endAt`
- `durationMillis`
- `readChars`
- `startPositionRatio`
- `endPositionRatio`

说明：

- “最近阅读”不应该自己被写成独立事实
- “按天汇总”也不应该自己成为事实来源
- 它们都应该从 session 派生

### 4.3 把 latest/day/heatmap 定义成投影

建议重新定义三类投影：

1. `LatestReadingProjection`
   作用：最近读过哪些作品

2. `DailyReadingProjection`
   作用：某一天读了哪些作品、总时长多少、总字数多少、会话数多少

3. `HeatmapDailyProjection`
   作用：热力图按日展示的单日指标

热力图的日投影至少应包含：

- `dateKey`
- `sessionCount`
- `workCount`
- `readMillis`
- `readChars`

这样 UI 才能真正支持：

- 按时长
- 按会话数
- 按作品数

而不是继续把“按次数”偷换成别的含义。

## 5. 页面职责重定义

### 5.1 最近阅读页

目标：

- 回到上次阅读位置
- 看当前读到哪
- 做删除和低风险修复

不应承担：

- 猜测式合并主入口
- 大量统计分析

### 5.2 按天汇总页

目标：

- 看某天读了哪些作品
- 快速回跳
- 看当天阅读强度

建议保留：

- 当天总时长
- 当天总字数
- 当天作品数
- 当天会话数

### 5.3 时间线页

目标：

- 回答“我是怎么读这本书的”
- 给用户明确的时间顺序

建议：

- 第一阶段不要再做展示层临时合并
- 先展示真实 session
- 如果要合并，必须把“合并组”作为正式视图模型存在

### 5.4 热力图

目标：

- 反映阅读活跃度
- 一键按日期过滤下方列表

建议：

- 默认按阅读时长
- 次选按会话数
- 不再使用“按次数”这种含混命名

## 6. 热力图的正确语义

建议正式支持以下三种模式：

### 6.1 按时长

表示：

- 当天总阅读时长

适合回答：

- 哪几天读得最久

### 6.2 按会话数

表示：

- 当天发生了多少次有效阅读会话

适合回答：

- 阅读行为是否频繁

### 6.3 按作品数

表示：

- 当天触达了多少本作品

适合回答：

- 阅读是否分散

不建议继续使用：

- `按次数`

因为这个名字没有稳定产品含义。

## 7. 合并逻辑的重定义

当前“按标题 + 作者近似”合并更像修复工具，而不是稳定主逻辑。

建议改成两层：

### 7.1 自动映射层

仅在高置信度时自动归并：

- 同一书架项
- 同一作品映射
- 用户已确认的跨源关系

### 7.2 修复工具层

保留手动合并，但明确定位为：

- 数据修复工具
- 不进入主路径

同时：

- 合并后要建立稳定映射
- 不能只改当前展示结果

## 8. 第一阶段推荐落地顺序

### 阶段 A：先止血

先做低风险收口：

1. 热力图“按次数”改名并改成真实指标
2. 时间线去掉展示层临时合并
3. 把阅读记录页的统计计算下沉到 service / view model

这三步不需要先改数据库主键，就能立刻降低语义混乱。

### 阶段 B：重建服务层

1. 新建 `ReadingRecordQueryService` 或等价 view model service
2. 让页面只消费：
   - latest model
   - daily model
   - timeline model
   - heatmap model
3. 页面不再自行算摘要和热力图

### 阶段 C：引入 `workKey`

1. 为阅读记录引入作品级身份
2. 补迁移策略
3. 明确书架 / 换源 / 阅读记录三者的身份绑定关系

这是最值钱但也最重的一步，应在前两阶段收口后进入。

## 9. 立即可做的改造项

如果下一轮直接动代码，建议优先做这三件：

1. 删除 `_mergeTimelineSessions()` 的展示层合并，时间线先展示真实 session
2. 把热力图模式改成：
   - `按时长`
   - `按会话数`
   - 可选 `按作品数`
3. 把阅读记录页中的：
   - `_buildHeatmapStats`
   - `_buildSummaryCard` 统计
   - 三层流拼接
   下沉到新的查询服务

## 10. 本轮结论

阅读记录当前最大的问题不是“热力图像抄来的”，而是：

- 产品语义没有自己的中心
- 数据模型和页面模型不一致
- 页面在替服务层补逻辑

所以最优路径不是先修热力图样式，而是：

1. 先纠正指标语义
2. 再收口页面职责
3. 最后引入作品级身份

只有这样，阅读记录才会从“兼容性附属页”变成真正可持续演进的阅读能力。
